# LLM Launcher architecture

LLM Launcher separates three decisions that used to be easy to mix together:

1. **Adapter metadata** says what engines and work surfaces exist.
2. **Compatibility policy** says which engine/surface pairs are supported.
3. **Builders** create the private command, environment, and temporary files for one validated launch.

The adapter seam is internal and fail-closed. It makes the existing routes easier to extend and test; it does not load arbitrary third-party Python or JavaScript into the launcher.

## Launch flow

```text
visible settings
      │
      ▼
request validation ──► compatibility matrix
      │
      ▼
engine builder ──► private local engine command/config or connected-engine bridge
      │
      ▼
work-surface builder ──► temporary Pi/OpenCode/Codex overlay or built-in Chat
```

`ENGINE_ADAPTERS` and `CLIENT_ADAPTERS` in `launcher.py` are the canonical descriptors. Each descriptor owns a stable ID, user-facing label, executable key, protocol, and built-in status. `/api/bootstrap` exposes a read-only public copy so the interface does not need a second naming or executable map.

`CLIENT_SUPPORT` is deliberately separate. Protocol compatibility is policy, not a side effect of an executable being installed. oMLX and LM Studio serve Codex's Responses protocol natively. Their launcher guard streams ordinary events immediately but holds the bounded terminal event long enough to correct an exact-ceiling false `response.completed` into the protocol-defined incomplete state; non-stream JSON gets the same correction. MTPLX is supported through the launcher's private, tested Responses-to-Chat bridge, which applies the equivalent rule from authoritative completion usage; that cell remains explicit because the bridge has a narrower fail-closed contract than a native endpoint. SwiftLM and Mference expose Chat Completions for Pi, OpenCode, and built-in Chat but not the Responses endpoint required by Codex. FreeToken exposes Chat Completions and Responses on a separately owned server; its compatibility row remains distinct because the launcher owns only the Mac-side bridges, not the runtime or model allocation.

For MTPLX Codex requests, `responses_bridge.py` converts text messages, standard function calls, function outputs, and namespace-contained function tools into Chat Completions. Namespace children receive deterministic short wire names and are restored to their original `(namespace, name)` pair in streamed Responses events. Reasoning, answer text, authoritative usage, tool calls, and explicit output-limit termination are translated independently. Hosted web search and remote Responses compaction are disabled for this fully local route. Images, custom/freeform tools, stored-response chaining, unknown fields, and any future shape that cannot be preserved are rejected before the upstream model request; the bridge never silently drops a tool or guesses a conversion.

`ENGINE_BUILDERS` and `CLIENT_BUILDERS` are the only dispatch maps. Unknown IDs fail explicitly. `validate_adapter_registries()` runs at startup and rejects a registry when descriptors, builders, executable keys, or compatibility rows are incomplete.

## Controller startup boundary

`Start LLM Launcher.command` resolves its own directory, accepts an explicit `LLM_LAUNCHER_PYTHON`, and otherwise checks fixed Homebrew/python.org plus shell-visible candidates for Python 3.10 or newer before forwarding all arguments. It does not rely on macOS `/usr/bin/python3` 3.9, and a missing compatible interpreter fails with a readable message before importing launcher code.

`serve()` holds an owner-only advisory lock in the launcher state directory for the whole controller lifetime. A contender reads only the bounded port record and treats it as live only when the loopback `/api/status` response carries the launcher server identity and valid JSON; it then opens that existing page and exits. A starting/stopping owner is retried for three seconds, stale records are overwritten only after acquiring the lock, and the active port is published only after the server has bound. TERM/HUP/Control-C cleanup stops every launcher-owned operation and process before closing the server and releasing the lock.

## Presentation boundary

Appearance is deliberately outside the launch contract. `theme.js` validates two independent browser-local names: one palette and one information level. It applies both to `document.documentElement` before first paint, falls back to Graphite and Focused when storage is absent or malformed, and never reads or writes the model/session/profile stores. `app.js` only reflects those values into menu state and a Show details toggle. A presentation change cannot call a builder, mutate `state.backend`, select a model, rewrite a visible control, start a request, or alter benchmark evidence. Frost is the optional polished light material layer; it changes presentation selectors only. Hub Console is intentionally scoped out of palette switching: its complete workspace owns black chrome, a pure-black terminal viewport, and fixed high-contrast ANSI variables in every appearance.

`route_preferences.js` owns a separate, versioned browser-local record containing exactly `backend`, `modelId`, and `client`. It bounds and validates all three values, ignores malformed or future-schema records, and selects only from a catalog rebuilt from the current installed engine, complete runnable artifacts, installed/built-in work surfaces, and protocol support. Startup prefers an exact remembered route, then the still-usable visible MTPLX/Pi default, then a deterministic installed route whose work-surface order leaves built-in Chat as the no-agent fallback. Applying the choice calls no backend endpoint and preserves every context, output, reasoning, sampling, KV, accelerator, prompt, project, and evidence control. Later writes occur only for a complete visible route that is still in that catalog.

Focused presentation is CSS-led progressive disclosure. It retains runtime/model/work-surface choices, context/output/reasoning, warnings, live run state, one compact exact-contract performance receipt, optimisation, Launch, Chat history/queue/thinking/answer, available transcript search, measured TPS, and Hub Console route/TPS. Performance receipt states use shorter plain-language labels in Focused, while their complete evidence summary remains in the accessible description/title. A fresh `trusted-engine` receipt marks only its exact winning runtime card; stale, tied, incomplete, and route-only evidence never receives a Best badge. Model-default Chat sampling leaves only the mode selector visible in Focused, while Custom or Detailed exposes every override. An idle Chat's empty telemetry and disabled transcript row remain in the document but are suppressed until a request or message makes them useful; live activity or authoritative usage reveals the compact performance row automatically. Saved Chat rows keep one primary action and put four maintenance actions behind an accessible More disclosure; cold-resume review keeps engine/model/action visible and folds secondary contract facts behind Route details, which Detailed opens automatically. Repeated helper copy, inactive compatibility explanations, guardrail/evidence/inventory cards, Route Check, Preview, expanded Chat telemetry, and secondary console metrics remain in the document and return in Detailed presentation. Inputs reveal their own helper copy on focus, and fidelity warnings stay visible. Calibration uses a page-memory-only disclosure flag: Focused keeps the locked-route summary, every eligibility/exclusion state, evidence, consent count, warnings, and progress, while the exact fact matrix, eligible-engine prose, and accelerator badges appear on demand; Detailed always reveals them. The disclosure cannot call a plan or mutation endpoint. The top bar similarly keeps Sessions, Models, Chats, Appearance, and one Tools menu; moving Calibration, Profiles, Sets, Runtimes, Rescan, and Manual into that menu does not duplicate their IDs, handlers, or state.

The performance receipt calls the side-effect-free `/api/benchmark/history` projection with a fixed representative suite—Agentic for coding surfaces and Standard for Chat—and the Fastest-total decision goal. `benchmark_history_request()` binds records to the model artifact, selected runtime, hardware/macOS fingerprint, work surface, context/output range, reasoning, sampling fingerprint, KV precision, suite/scenario contract, greedy-quality fingerprint, and complete eligible-engine matrix. Only a strict verified current-route record or trusted complete shootout becomes an Apply action. Fresh, stale, tied, incomplete, missing, and unavailable states remain distinct; stale/tied/route-only paths open Benchmark Lab, missing cross-engine evidence opens the consent-gated Calibration plan, and the read-only receipt itself cannot load a model, change a control, or promote scanner availability into a speed claim.

## Model catalog boundary

`scan_models()` is the canonical artifact and engine-capability scanner. It also adds virtual FreeToken model records only from the last saved, explicitly discovered server catalog. `model_library_inventory()` projects that data through `ENGINE_ADAPTERS`, `CLIENT_ADAPTERS`, `CLIENT_SUPPORT`, and installed-or-connected status into a read-only compatibility report. `/api/model-library` returns the report and the same raw scan used by the normal model selector, so choosing a library route cannot drift from launch validation.

The report distinguishes artifact compatibility from a currently runnable route. A ready route requires a complete artifact, compatible scanner capability, installed engine, installed or built-in work surface, supported protocol cell, and at least one enforceable reasoning choice. It summarizes only already-matched local benchmark records; the presence of MTP, DFlash 2, ANE, or SSD-streaming capability is never promoted into a speed claim by the catalog.

Opening or refreshing Model Library may read known model folders, local command versions, runtime metadata, the saved FreeToken catalog, and launcher-owned evidence. It allocates no port, creates no run directory, starts no process, contacts no network service, and writes no state. The browser's **Use with …** action changes only the ordinary visible engine/model selection and preserves the current work surface. FreeToken catalog refresh is a separate explicit reconnect action.

## SSD-streaming boundary

SwiftLM and Mference are registered adapters, not generic fallbacks for any large directory. `ssd_streaming_model_profile()` first identifies a complete MoE and records its weight-to-installed-memory ratio, native expert top-k, format, and immutable-source proof. SwiftLM admission then checks an explicitly supported MLX architecture family, including upstream's released Qwen3-Next path. Mference admission mirrors its cheap trusted-receipt boundary: regular bounded metadata, `GTURBO` v1, known flags, one pinned streaming architecture signature, exact receipt/directory/manifest binding, identical declared file sets and hashes, safe regular paths, matching sizes, and the complete non-empty expert-layer range. Large payload hashes remain Mference's runtime responsibility. A newly named, moved, stale, or structurally different model therefore stays visible with its rejection reason instead of reaching a builder by resemblance. Qwen3.8-Flash-Next is intentionally detected as a distinct candidate but rejected until an upstream runtime accepts that exact architecture.

Normal in-memory models remain on oMLX, LM Studio, or MTPLX. When an MoE reaches the guarded oversized threshold, the selectable engine set narrows to the two SSD adapters so an in-memory result cannot masquerade as an out-of-core comparison. Both builders preserve the checkpoint's native expert top-k and keep speculative decoding off; SwiftLM exposes bounded prefill chunk selection, while Mference exposes only its prompt-cache and queue controls. MferenceServer accepts six fixed windows from 4,096 through 128,000 tokens, so direct launches reject any other value before allocating a process. Cross-format Calibration visibly normalises only this SSD lane to the largest common window at or below the request and applies that context together with the measured engine result, preventing a saved 128,000-token result from reopening as an unmatched 131,072-token request.

Cross-format Calibration requires a cryptographic comparison identity derived from the same immutable repository and revision. A matching name, tensor geometry, or self-declared origin is insufficient. Each engine receives a fresh process and the same generated agentic contract; first-turn and warm-prefix stages remain separate, and the saved evidence binds generation TPS, TTFT, memory/thermal conditions, natural SSD cache state, runtime version, artifact fingerprint, and source identity. The launcher does not claim it can purge macOS's file cache, and an incomplete pair can be launched independently but cannot produce a cross-engine winner.

## Connected-engine boundary

FreeToken is registered as a first-class engine without pretending its released CUDA runtime runs on this Mac. `/api/freetoken/connect` is an explicit, operation-locked network action: it validates a credential-free HTTP(S) origin or `/v1` base, resolves and rejects link-local, multicast, and unspecified targets, disables redirects, verifies TLS, bounds the `/v1/models` response, and writes an owner-only connection record. Public status returns the configured endpoint for the connection editor plus connection identity, context, server label, and model catalog; it returns only `hasApiKey`, never the upstream key itself.

Each discovered model is a virtual remote record bound to the connection identity and exact served-model ID. `build_freetoken()` revalidates both, creates an owner-only `freetoken-bridge.json`, assigns a new local key, and starts only `freetoken_bridge.py` on loopback. That bridge accepts a bounded Models/Chat Completions/Responses path set, replaces authorisation, enforces the selected model, follows no redirect, verifies TLS, and guards response size. A normal session still adds `session_proxy.py` in front so every attached Pi/OpenCode/Codex/Chat surface receives a distinct bearer key plus the ordinary scheduler/TPS contract. Neither upstream endpoint nor key reaches a surface.

The ownership boundary is asymmetric by design. Stop, Route Check cleanup, or idle timeout terminates the launcher-owned session proxy and FreeToken bridge only; no request to stop or unload the upstream server is made. Capacity reporting describes only the local bridges/work surface because weights, KV cache, and MoE policy remain on the server. FreeToken is excluded from Mac-local Calibration, Benchmark Lab, Runtime Manager, and automatic cross-engine winners; live authoritative usage/TPS remains visible. A native Apple-Silicon port is a separate backend project, not part of this connection adapter.

## Model acquisition boundary

Model Acquisition is deliberately separate from the read-only catalog. `/api/acquisition/search` and `/api/acquisition/inspect` are explicit public-network operations. The Hugging Face subprocess environment removes known Hub token variables and sets `HF_HUB_DISABLE_IMPLICIT_TOKEN=1`; the interface accepts no credentials. Search results are bounded and sanitized. Inspection validates one `owner/repository` plus an optional revision, resolves it to an immutable commit, and inventories that pinned tree before any destination is created.

`model_acquisition_variants()` is the only file-selection policy. It accepts a standard root-level MLX checkpoint with metadata and complete safetensors weights, or exposes each GGUF quantisation/complete shard group independently. A request can select at most 128 files and 512 GiB. Draft-only components, custom root code, gated/private/disabled repositories, and files marked unsafe fail closed. Paths are validated as relative Hub paths before they enter either a plan or local path join.

`build_model_acquisition_plan()` is side-effect free. Its identity binds the schema, repository, pinned commit, exact variant, and fixed known destination. It rejects collisions unless the existing folder contains a matching launcher marker; checks current remaining bytes plus a 4 GiB disk reserve; and reports, without treating as a download blocker, a conservative weight bytes plus 8 GiB memory fit. Engine compatibility in this plan is only a prediction. The canonical post-download `scan_models()` and Model Library report remain authoritative.

`ModelAcquisitionManager` owns at most one download or verification worker and participates in the same global operation exclusion as launches, route checks, benchmarks, Setup Assistant, runtime selection, attachments, and ANE tuning. Start requires a fresh in-memory plan ID, exact server-generated `repository@commit` confirmation, and explicit license review. Only then may it create the destination and owner-only acquisition marker. The command is a fixed `hf download` argument vector containing the pinned revision, exact filenames, fixed local directory, bounded workers, and no shell. Cancellation terminates only that downloader and preserves files/cache metadata for resume.

Subprocess success is insufficient. `verify_model_acquisition()` rejects symlinks and verifies every selected file's exact size plus every available LFS SHA-256 digest. MLX results must also pass weight-shard completeness and bounded safetensors inventory checks; GGUF results must have valid magic bytes. A verified marker is written only after those checks. The UI then routes completion back through Model Library; it never directly promotes the plan's engine predictions or a speed winner.

## Runtime update boundary

`RUNTIME_UPDATE_CATALOG` is a deliberately small, locally audited trust root rather than a live “latest” query. Each supported oMLX track fixes the release tag, full source commit, exact CPython 3.11 universal wheel URL, and GitHub-published SHA-256. `build_runtime_update_plan()` is side-effect free and binds that artifact to the detected interpreter, versioned launcher-owned destination, current installed provenance, free-space reserve, action, and rollback selection. Existing non-exact directories and symlinked roots fail closed.

`RUNTIME_RELEASE_CATALOG` is a separate, presentation-only audited snapshot for all three engines. It records the reviewed official release identity, source page, bounded highlights, and safe evaluation order, then compares those values only with local version metadata. It performs no live update lookup. Missing, unparsable, older, and newer-than-catalog versions remain distinct states; only an exact semantic match is labelled audited current. This catalog can recommend the vendor-owned LM Studio or MTPLX updater without granting the launcher authority to modify either app.

`RuntimeUpdateManager` accepts only an unexpired in-memory plan plus its exact confirmation and explicit review flag. An install downloads to launcher-owned cache with HTTPS-only curl arguments, verifies the complete root-wheel digest, and audits that wheel's direct-source metadata against four catalogued public GitHub repositories at full commits. In isolated mode pip may build only those four named sources; every other dependency must be a wheel. The resulting private wheelhouse is hashed and then installed with `--no-index --no-deps`, so the install phase cannot resolve or fetch anything. Version output, package metadata, `pip check`, the server command surface, and native-kernel status are checked in staging. Generated virtual-environment launchers are then rebased to the approved final directory before atomic promotion, and every smoke test is repeated from that final path before the owner-only manifest records trust. A failed final-path check removes only the newly promoted, unselected copy. Only the first-party oMLX wheel is anchored by the release publisher's SHA-256; the full-commit source identities and staged dependency hashes are disclosed evidence, not a claim that upstream published a complete dependency lock.

Verification of an existing managed copy requires either its owner-only manifest or Python `direct_url.json` to contain the audited official artifact hash. Cancellation terminates only the owned download/install subprocess, deletes only the uniquely named staging directory, preserves resumable artifact bytes, and leaves `BINARIES`, shell PATH, other installations, servers, models, and preferences untouched. Promotion never selects the new candidate; `select_runtime_candidate()` remains the separate explicit activation and rollback mechanism. Runtime Update participates in the same global operation exclusion as sessions, attachments, downloads, route checks, benchmarks, and ANE tuning. LM Studio and MTPLX stay outside this installer because their app/runtime update lifecycles are vendor-owned.

## Runtime promotion boundary

`build_runtime_promotion_plan()` is a side-effect-free contract over one selected oMLX copy, one different launcher-managed candidate with verified official-wheel provenance, their exact executable-byte/stat revisions, a stable model fingerprint, hardware identity, and a normal Benchmark Lab workload contract. The internal job forcibly removes accelerator and precision confounders: AR only, full-precision KV, ANE off, balanced burst, identical reasoning/sampling/context/output, generated prompts, and cache-isolated loads. Matching reruns alternate which copy loads first by reading—but never mutating—the bounded evidence store during planning.

`RuntimePromotionManager` inherits the existing benchmark measurement primitives but owns separate state and `runtime-promotions.json` evidence. `normalized_request(..., purpose="runtime-promotion", runtime_binary=...)` accepts an override only for oMLX, only for an exact currently discovered candidate, and stores it on `LaunchPlan`; `build_omlx()` uses that path for the private process without mutating `BINARIES` or runtime preferences. One route runs at a time, is stopped through `RunManager`, and receives the same warm-up, greedy quality probe, authoritative usage checks, workload samples, public resource telemetry, and bounded cancellable cooldown used by Engine Shootout. Runtime Promotion is a first-class globally exclusive operation, so launches, attachments, updates, downloads, route checks, Benchmark Lab, and ANE tuning cannot overlap it.

No partial record is saved. A complete result requires equal quality hashes and completion-token counts, equal sample contracts, public thermal/Low-Power/memory starts within the existing 512 MiB tolerance, at least 1.03× median and worst paired performance, no more than 512 MiB extra peak pressure, and no worse public thermal state. The evidence record contains identities and metrics, never prompt or completion text. `promote()` is a second explicit operation: it accepts only the exact server-generated result confirmation, requires evidence younger than seven days, recomputes both executable revisions and candidate provenance, verifies that the measured baseline is still selected, then delegates to the ordinary launcher-owned selection function. It never removes either copy, so rollback remains the explicit candidate selector.

## ANE tuning boundary

`ANETunerManager` owns one temporary oMLX route and never edits global oMLX settings. Base admission requires the selected 0.6.3rc2-or-newer runtime, its native Qwen-kernel self-check, a complete dense Qwen affine 4/5/6/8-bit group-size 64/128 checkpoint, and checkpoint bytes plus an 8 GiB installed-capacity reserve. It fixes the benchmark shape at 2,048 tokens, sanitises the upstream result surface, and saves a recommendation only when a positive private-log ANE operation trace exists, no memory/runtime failure appears, and measured prefill clears the 3% noise floor. Evidence is bound to the model, runtime, Mac, and fixed shape; cancellation and failure save no partial result.

CPU sharing is a second, explicit admission contract inside the collapsed advanced candidate pool. `ane_cpu_sharing_profile()` reads only bounded safetensors headers and requires a separately prepared checkpoint whose complete floating-tensor set and every matched MLP gate/up scale pair are F16; BF16 or mixed checkpoints fail closed. Down and GDN CPU grids are enabled only when their own scale families are present. CPU tuning also requires checkpoint bytes plus a 16 GiB capacity reserve. The job records a digest of every tensor name, dtype, shape, and shard, and `valid_ane_recommendation(..., allow_cpu=True)` bounds gate/up, down, and GDN fractions to the installed upstream grids, requires a real CPU worker count, and rejects impossible combined splits. `build_omlx()` rereads the FP16 profile, reserve, digest, and model-bound evidence immediately before writing the measured CPU fields to the run-private `model_settings.json`. Ordinary BF16 ANE/GPU evidence remains backward compatible, and the fastest-safe preset continues to disable all approximate ANE paths.

`build_ane_fp16_clone_plan()` is the only admission path from an eligible BF16 checkpoint to a CPU-sharing clone. Its short-lived in-memory contract binds the exact source artifact and tensor-profile fingerprints, destination, selected oMLX runtime/Python, audited helper digest, source byte inventory, and a source-size-plus-4-GiB disk reserve. Planning is read-only and rejects destination collisions, symlinks, non-regular files, unsupported floating dtypes, incomplete gate/up pairs, incompatible quantisation, or a mismatched scanner fingerprint. `ANEFP16CloneManager` requires that exact plan ID, server-generated confirmation, and explicit approval, re-plans immediately before work, and participates in the launcher's global operation exclusion.

The helper is derived from oMLX v0.6.3rc2's tagged `tools/clone_mlx_model_fp16.py` and runs under the selected runtime Python with no shell and Hub credentials removed. It validates every shard for finite/range-safe BF16/F16 content before creating a uniquely named sibling staging directory, converts BF16 tensors shard-by-shard, and retains packed integer tensors. Cancellation or failure may delete only that exact staging name. Before atomic rename, the manager proves the source fingerprint remained unchanged, the clone is complete and all-FP16, tensor names and shapes match, every source BF16/F16 tensor became F16, every packed dtype stayed unchanged, and the staged tree contains only regular files. The original directory is never written, and a completed result is merely rescanned and explicitly selected; it does not start tuning or inference.

## Builder contract

An engine builder receives a validated `LaunchPlan` and the selected model's capability record. It may create files only inside that run's private directory and must populate:

- `engine_argv`
- `engine_env`
- the private served-model ID
- any generated runtime secret

For a local engine those fields start or address the model runtime. The FreeToken builder is the explicit connected-engine exception: its `engine_argv` starts the private local upstream bridge, while the separately operated server retains model ownership. The same cleanup machinery may terminate that bridge but has no upstream stop authority.

A work-surface builder receives the same plan plus a private `ClientRoute`. It must populate `client_argv` and `client_env` without rewriting the user's normal Pi, OpenCode, Codex, or runtime configuration. Built-in Chat has no external executable.

Generated secrets stay in the controller and process environment. They must not appear in bootstrap metadata, public run state, logs, exported Chat history, or command previews.

Active Chat request controls have a narrower mutable boundary than the loaded-engine contract. `/api/chat/settings/get` resolves one exact controller-owned primary or attached Chat surface, and `/api/chat/settings/update` reruns `validated_chat_settings()` before atomically replacing only that surface's system prompt and sampling dictionary. `RunManager.chat_request()` serializes the next request body under the same lock, so a turn observes either the complete old contract or the complete new contract—never a partial update. Backend, model identity, context, response ceiling, reasoning, ports, engine options, commands, and secrets are not accepted by the update endpoint. A stale run/surface fails closed, invalid settings leave the previous dictionary intact, and status/event output exposes only the setting state needed by the local UI rather than route credentials. A queued browser message uses the contract active when it is converted into a request; no update reloads model weights.

Chat Context Packs preserve the same boundary. The browser may send bounded text from files the user explicitly selected, but the backend accepts no file path and performs no project-tree read. It validates visible relative names and content limits, prepends a locked data-not-instructions notice, and includes the pack only in the current request. Context bodies are deliberately absent from `chat-history.json`, branch metadata, and Markdown export.

Workspace Context extends that browser-owned boundary rather than weakening it. `workspace_context.js` contains the independently tested path policy, lexical ranking, excerpt, and conservative request-budget core. The browser receives files only through an explicit directory picker; skips dependency/build/cache paths, likely credentials, generated lockfiles, binaries, oversized files, and excess index bytes; and keeps the remaining index in page memory. Each request sends at most 12 ranked excerpts through the same backend Context Pack validator. The backend therefore sees bounded named text, never a directory handle or path it could open. A locked system instruction tells the model that excerpts may be incomplete and requires visible filename citations when it relies on them.

Composer and queue recovery form a browser-only boundary. `chat_drafts.js` validates, caps, prunes, migrates, and removes unfinished composer text in `sessionStorage`; `chat_queue.js` independently does the same for ordered waiting-message IDs and text. `app.js` scopes both stores to the active Chat surface and saved conversation. Neither store contains system prompts, Context Packs, Workspace indexes or excerpts, model responses, credentials, or backend route state. The active queue presents only a count and bounded next-message preview until its management disclosure is opened. Queue recovery is fail-closed: restored entries open for review, remain paused, require an explicit resume action, and a turn that cannot start is reinserted at the front and paused. A refresh can reopen the matching locally saved transcript before restoring its draft and paused queue, while a missing transcript converts only that recoverable text into a new unsent session.

Streaming transcript position is an independent browser-only concern. `chat_scroll.js` normalises scroll geometry, defines the near-tail threshold, clamps restored offsets, and resolves each redraw as stale, follow, restore, or preserve-user. `app.js` follows output only while the reader remains at the live tail; wheel, touch, pointer, or scroll-navigation-key intent wins over a pending animation-frame restoration, and an older redraw callback cannot overwrite a newer one. A deliberate upward scroll therefore survives complete DOM re-renders and exposes an explicit Jump to latest action. Open reasoning-panel IDs also survive each render. This state contains no message content and is never persisted.

Current-transcript navigation remains in that browser-only presentation boundary. `chat_transcript.js` normalises a query of at most 160 characters, builds at most 512 matching-message records from the already visible transcript, assigns deterministic Turn/Reply landmarks, and wraps previous/next navigation without touching History or a model request. `app.js` highlights only existing text nodes with bounded `<mark>` elements, keeps the active result selected through streamed re-renders, opens a runtime-emitted reasoning card only when the active match is inside it, and pauses live-tail following while the reader navigates. Query, match, and active-result state are never persisted. New messages may include a validated timezone-aware creation timestamp in owner-only History and interrupted-turn recovery; older messages without one remain undated, and timestamps never enter the model request.

Stream termination is another fail-closed protocol boundary. `chat_stream.js` accepts only a short allowlist of explicit token/output-limit reasons from Chat Completions finish/stop fields or Responses incomplete-detail fields. It rejects generic incomplete states, ordinary stops, tool calls, content filtering, malformed values, and response text that merely looks cut off. `app.js` stores the resulting boolean only on assistant messages, presents one compact response-limit cue, and leaves continuation as a separate user action. History validation prevents a user message from asserting the flag; checkpoints, branches, and Markdown export preserve it without adding the request-only continuation instruction.

Final-answer presentation is a separate inert-content boundary. `safe_markdown.js` converts bounded assistant text into a small structural model for headings, paragraphs, lists, tasks, quotes, tables, rules, inline formatting, links, and code; it never emits or accepts an HTML node. `app.js` constructs the corresponding page elements with `textContent` and text nodes, permits only credential-free `http`/`https` links with opener and referrer isolation, renders image syntax as an ordinary labelled link, and keeps raw HTML visible as text. Open code fences are valid streaming structures rather than executable fragments, while block, token, table, nesting, and character limits bound rebuild cost. Code-copy and message-copy read only rendered local text; message copy remains available during another stream because it cannot mutate the conversation. Revision controls are grouped behind one per-message disclosure, with an authoritative output-limit continuation kept directly visible. User messages and runtime-emitted reasoning deliberately bypass Markdown so the visual hierarchy cannot change their meaning.

Active streaming turns use a distinct backend-owned recovery boundary. `app.js` gives each browser tab a random `sessionStorage` identifier, reserves a History UUID before sending, and writes a throttled snapshot containing only the accepted visible prompt, visible transcript, partial model output/reasoning, small usage fields, and display route labels. `RunManager` rebuilds the current Chat plan before accepting a checkpoint, then binds server-authoritative run, attachment, backend, and model metadata. The owner-only `chat-turn-journal.json` is capped at eight entries, eight million characters, and seven days; it excludes system prompts, Context Packs, Workspace indexes/excerpts, credentials, runtime secrets, and API keys. Recovery atomically removes and promotes one matching entry into History with its user/assistant pair marked excluded and the assistant marked stopped/interrupted. A completed History record with an equal or newer timestamp wins and discards the stale journal, while successful final saves clear their entry. Conversation history retains both the original and latest validated route metadata so reusing a currently loaded but different model is explicit rather than a hidden swap.

## Warm routing, request-relay, and cache-observation boundary

`RunManager.warm_route_plan()` is the side-effect-free bridge between the main visible Launch action and the existing surface-attachment path. It canonicalizes the visible request, then compares only the resident-engine contract: backend, model ID and checkpoint fingerprint, context, output ceiling, reasoning, and validated engine options. Work-surface choice, agent host, project, and Chat prompt/sampling remain per-surface overlays, but the normal compatibility, executable, reasoning, and attachment-limit checks still apply. The plan creates no port, file, engine, Hub Console, or Terminal. Its confirmation hashes the active owner run, complete canonical request, and loaded contract; `warm_attach()` rebuilds that plan under the operation lock and rejects stale or changed confirmations before delegating to the ordinary `attach_surface()` implementation. A warm attach can therefore create only the already-audited per-surface overlay and never a second engine command.

Session Sets compose that same boundary without introducing another launch implementation. `session-sets.json` contains one canonical primary request plus at most eleven surface overlays; load and save paths whitelist fields and re-run the ordinary launch-profile validator, excluding content, credentials, ports, private options, commands, process state, and console data. `build_session_set_open_plan()` is read-only: it either obtains normal capacity admission for one primary load, proves an exact warm engine contract and computes the multiset of missing launcher-owned surfaces, reports an already-open no-op, or blocks. Its confirmation binds the saved revision, owner run, shared engine contract, and exact missing overlays. `SessionSetRunner` rebuilds that plan under `SESSION_OPERATION_LOCK`, starts the primary through `RunManager.start()` only when needed, waits for the same run to reach Running, then calls `attach_surface()` for each remaining overlay. Stop affects only not-yet-opened overlays; completed surfaces and the model remain. External Terminal records are excluded from existing-surface matching because relay registration cannot prove that an unowned Terminal window is still alive.

Every normal session starts one `session_proxy.py` process before its model becomes available. The owner-only configuration contains the upstream engine key, a separate controller key, and one random bearer key for the primary surface. Each warm or Sessions attachment registers another UUID plus a distinct bearer key through the controller-only route; the engine key is never given to Chat, Pi, OpenCode, or Codex. The relay accepts only loopback traffic and a fixed OpenAI-compatible path set, replaces client authorisation before forwarding, caps Chat output, and reuses the Codex Responses transformation for output/reasoning enforcement. A relay loss is fatal to the normal session because continuing would make the public route misleading and strand every surface.

For streamed Chat Completions, the relay also corrects one observed local-runtime protocol fault: a server may emit exactly the enforced `max_tokens` count but label the terminal choice `stop`. The relay passes ordinary content events immediately, holds only the bounded terminal SSE tail until authoritative usage arrives, and changes that exact false-normal boundary to `length`. Pi can therefore expose a recoverable continue warning in both Hub Console and Terminal. No prompt, reasoning, or response text enters the request registry or persistent state.

Pi RPC defines `message_end.message` as authoritative rather than promising that every preceding delta reaches an embedding UI. Hub Console therefore keeps only the current bounded block assembly in session memory, compares it with the final message, appends any missing suffix, and labels a mismatched recovered block instead of erasing already visible output. A settled assistant message containing reasoning but neither final text nor a tool call receives a local **No final answer** continuation hint. The assembly is cleared at message end/settle and never enters persistent state.

`RequestScheduler` is an in-memory, bounded FCFS admission gate around generation POSTs. Its lane count is derived from the exact loaded contract: one for the launcher's current oMLX and MTPLX routes, or LM Studio's selected parallel count. At most 64 requests may wait; control/model-list traffic does not consume a generation lane. Cancellation sets only the selected request's event and closes its upstream connection when active. `ResponseMetrics` observes at most 1 MiB of transient SSE/JSON framing to locate the first actual output event and runtime-supplied usage integers, then publishes decode and end-to-end TPS; for LM Studio only, an allowlisted finite numeric subset of response `stats` can supersede that calculation with engine TPS/TTFT/generation time and MTP accepted/total counts. Unknown sources, malformed values, text, and draft-model IDs are discarded. It never estimates tokens or changes relayed bytes. Public activity contains a random request ID, registered surface UUID/type, protocol, state, queue position, timestamps/durations, relayed-byte count, optional numeric token/performance facts, HTTP status, and result. It contains no request/response body, reasoning text, tool data, model ID, project data, or key, persists nothing, and retains at most 32 completed rows until the relay exits.

MTPLX 2.9.1+ adds a separate local `/v1/mtplx/flight` observation. `RunManager.request_activity()` version-gates the call before network access and treats every timeout, malformed response, or unsupported version as optional telemetry loss rather than route failure. It publishes a bounded numeric subset only when exactly one private-relay request and one active flight match the served model and elapsed timing: phase, elapsed seconds, prompt/generated/context token counts, current/average TPS, reasoning/content character counts, MTP acceptance by depth, and stall age. It discards the engine request ID, session ID, model string, recorder path, recent-flight history, and generated-text tail. It never persists the subset, exposes it to an external surface, or assigns it when more than one request/flight makes attribution ambiguous. The relay remains the authority for scheduling, cancellation, completion history, and final usage-derived TPS.

oMLX 0.6.3rc2+ exposes richer live records through protected `/admin/api/activity`. The launcher does not disable that protection: it signs in to its own ephemeral oMLX process with the already-private engine key, keeps the returned admin cookie only in the private `LaunchPlan.secrets` object, serialises telemetry reads, retries one expired-cookie response, and deletes the cookie on route stop. It then discards every engine request ID, model ID, unrelated loaded-model record, memory/cache/DFlash object, and free-form detail. Only one exact served-model record plus one relay request with matching elapsed timing may publish prefill/decode phase, prompt progress, prompt/generated/context tokens, engine TPS, and stall age. Unsupported versions are not probed. A missing protected endpoint degrades only this optional summary; it cannot fail inference or alter the relay.

An agent surface chooses either `terminal` or `console` ownership. Terminal keeps the existing generated per-run overlay and external macOS handoff. Console validates that the absolute executable still equals the scanned Pi/OpenCode/Codex binary, then starts it in a new launcher-owned PTY process session with only the already-built per-run environment. Pi Hub sessions add the agent's supported `--mode rpc` flag, disable PTY echo, and consume strict JSONL events. The controller requests the current session messages once, translates later user/thinking/text/tool/queue events into a safe append-only ANSI transcript, and sends `prompt` or `abort` commands. Follow-ups are held in a bounded launcher-owned queue and submitted one at a time after `agent_settled`; Clear queue therefore also works with installed Pi versions that do not yet expose their own `clear_queue` command. A bounded periodic `get_state` probe repairs missed settle events only after Pi has acknowledged prompt preflight, and a final unterminated JSONL record is consumed before process teardown. Interactive extension requests are sanitised, retained only in memory, and answered through an ID-bound `extension_ui_response`; the browser renders only confirm, select, input, and editor shapes. This avoids reconstructing Pi's continually redrawn TUI while preserving Terminal mode for workflows that need it. `AgentConsole` retains at most 2 MiB of translated or raw output in memory, exposes absolute base/end revisions for loss-aware refresh recovery, returns at most 128 KiB per authenticated controller read, accepts at most 64 KiB per input call, and bounds terminal dimensions. The browser maintains one decoder, VT buffer, absolute offset, seen offset, and input queue per surface; switching the active tab therefore cannot redirect an already queued command or key sequence. It polls only the active console for content while the ordinary content-free status snapshot supplies background activity and unread revisions.

`terminal_core.js` keeps character and SGR-style cells in parallel across the main screen, alternate screen, bounded scrollback, erasure, insertion, deletion, resize, and cursor overwrites. A row shrink moves displaced main-screen rows into the same bounded scrollback, and a later grow restores them, so responsive layout changes preserve the newest transcript rather than clipping it. It accepts only a fixed presentation subset: reset and common emphasis flags plus standard, 256-indexed, and bounded RGB foreground/background colours. `CSI 3J` clears scrollback without changing visible cells. Styled output is coalesced and capped at 4,096 style runs, after which presentation fails safely to a plain-text tail. `app.js` maps standard colours through CSS variables scoped to the pure-black terminal viewport and converts only validated numeric indexed/RGB values into CSS. It renders terminal content exclusively through `textContent`, text nodes, constrained `<span>` elements, and bounded `<mark>` search nodes; terminal bytes never become HTML or CSS input. Pi RPC text is stripped of control bytes before trusted launcher headings are added. Search segmentation preserves style boundaries and copy still uses the same plain bounded screen.

Refresh recovery in `sessionStorage` is owner-scoped and contains only version, active surface ID, visibility, and numeric seen offsets; terminal content is rebuilt from the in-memory backend buffer and is never persisted. Stop/restart affect only that agent; route cleanup terminates every owned console before the relay/engine. External Terminal handoffs remain outside launcher ownership.

Idle unloading is controller policy rather than relay authority. It is off at every start, begins counting only after explicit selection, pauses while relay activity is active or queued, and invokes ordinary owned-route cleanup when the timeout expires. It fails closed when the relay is unavailable. For FreeToken that cleanup is labelled auto-close and ends only the local bridges; the server/model is unchanged. LM Studio is permanently ineligible because its shared unauthenticated service may have clients that independently know the engine port; relay silence cannot prove that model slot is unused.

Cache observation is deliberately a different contract. `Handler.stream_chat()` continues relaying upstream bytes unchanged while extracting only boolean output presence and authoritative usage/cache integers from parseable built-in Chat events. The trusted request carries only the server-validated owner and attachment IDs. `RunManager.record_chat_cache_observation()` accepts observations only while that exact Chat surface belongs to the current running normal session, sanitizes every value, and retains at most 64 rows in memory. The public aggregate distinguishes engine residency, configured versus engine-managed cache policy, telemetry coverage, reported zero reuse, and confirmed cached-token reuse. Timing is shown as timing and never used to manufacture a cache hit. No observation contains prompt, response, reasoning, system-prompt, Context Pack, Workspace, project, credential, or API-key data; all rows clear on the next start or stop. Pi/OpenCode/Codex are visible to request scheduling, but the relay deliberately does not parse their response bodies into cache evidence.

## Route verification contract

Route Check deliberately reuses `normalized_request`, the registered engine/client builders, `RunManager`, model discovery, and the Codex Responses guard. It is not a parallel launcher implementation. The read-only plan uses session admission without allocating a port or creating files; the consent-gated live pass runs with purpose `route-check`, never invokes the client launcher, and always converges on normal owned-route cleanup.

The protocol probe is selected from the client descriptor: Pi, OpenCode, and built-in Chat use Chat Completions, while Codex uses its actual guarded Responses address and client key. Every live pass uses fixed synthetic text and a 64-token ceiling. Agent surfaces also receive a harmless function schema. Public results contain only event counts, text/reasoning character counts, token usage returned by the runtime, latency, and pass/advisory/fail states—never generated response content or credentials.

A missing model ID, rejected core protocol, empty response, or rejected agent tool schema fails closed. JSON fallback, omitted authoritative usage, absent separately exposed reasoning, or a model choosing text after accepting a tool schema is visible as an advisory where the route itself remains usable. A bounded smoke test proves the checked contract at that moment; it does not claim universal compatibility with every future tool or MCP payload.

Verified Quick Launch joins measurement, verification, and launch without weakening those boundaries. A pass or advisory creates a memory-only receipt only after owned-route cleanup succeeds. The receipt expires after ten minutes and binds the Route Check job and contract to the exact visible request, model fingerprint, selected runtime version and executable revision, and adapter schema. `/api/launch` recomputes that identity and validates the receipt while holding the session-operation lock before it creates a run directory or starts anything. Changed settings, replaced model bytes, a different runtime, expired or missing evidence, failed cleanup, and process restart all fail closed.

## Adding an inference engine

1. Add its known executable candidates and `BINARIES` key.
2. Add one `ENGINE_ADAPTERS` descriptor.
3. Add a full `CLIENT_SUPPORT` row, including explicit reasons for unsupported surfaces.
4. Add model-scan capability data for that engine.
5. Add a dedicated engine builder and register it in `ENGINE_BUILDERS`.
6. Add optimiser and benchmark policy only where the engine can preserve the full visible contract.
7. Extend the route tests across every supported work surface and prove user configuration files remain unchanged.

## Adding a work surface

1. Add its executable to `BINARIES`, unless it is built in.
2. Add one `CLIENT_ADAPTERS` descriptor with the actual wire protocol.
3. Add the surface to every engine's compatibility row.
4. Add a dedicated builder and register it in `CLIENT_BUILDERS`.
5. Define its reasoning, context, output, and attachment rules explicitly.
6. Add command/config exactness tests and verify secrets never enter arguments or public state.

The registry completeness test intentionally makes partial additions fail. A new descriptor without a builder or a missing compatibility cell cannot silently fall through to another adapter.

## Stable safety invariants

- One normal launcher session owns at most one model allocation.
- Attached work surfaces reuse the loaded route and never build a second engine command.
- The main warm action is enabled only by an exact canonical resident-engine match and is revalidated server-side before attachment.
- Every launcher-created normal-session surface uses one shared private relay and a unique bearer key; the upstream runtime key is never exposed to a surface.
- Generation admission is bounded FCFS with the exact loaded lane contract, and one request can be cancelled without inventing control over an external Terminal process.
- Request activity is session-only, content-free, capped at 32 completed rows, and never presented as coverage of independent engine clients. Completion TPS comes from exact allowlisted LM Studio response stats when present or from runtime-reported token counts plus relay timing. oMLX 0.6.3rc2+ and MTPLX 2.9.1+ live TPS/context is attached only to an exact one-relay-request/one-engine-record match, publishes no engine IDs, admin credential, or text tail, and fails closed to unavailable rather than estimating or guessing attribution.
- Hub Console owns only its exact PTY children, caps each output buffer in memory, persists no transcript, and can switch, stop, or restart one agent without unloading the shared model. Tab recovery persists only identifiers, visibility, and numeric seen offsets. External Terminal handoffs remain unowned.
- Idle unloading is off by default, pauses for admitted or queued work, fails closed without relay evidence, is unavailable for LM Studio's shared service, and closes only local bridges for FreeToken.
- Engine residency, cache configuration, and a runtime-reported prefix hit are separate public states; cache timing alone is never hit evidence.
- Cache observations are session-only, number-only, capped at 64, and limited to controller-relayed built-in Chat turns.
- Runtime and work surface receive the same visible context, output, reasoning, sampling, and precision contract.
- Existing user configuration is never rewritten; integrations use per-run overlays and command-line layers.
- Unknown adapters, unsupported protocols, missing executables, and incomplete model capabilities fail before a process starts.
- Model Library is a projection of canonical scan and adapter policy, not a second compatibility database; refresh is read-only, reuses only an explicitly discovered FreeToken catalog, and selection starts nothing.
- Model Acquisition resolves public metadata before any write, disables implicit Hub credentials, selects one bounded standard artifact, pins every file request to an immutable commit, never overwrites an unowned destination, and cannot run concurrently with another launcher-owned operation. Download completion is not trusted until independent file and structure verification passes.
- Automatic performance choices require matching local correctness and measurement evidence.
- Connected FreeToken routes never enter the Mac-local benchmark matrix or claim local capacity; their live TPS uses only upstream-reported token counts, and cleanup never claims control of the upstream service.
- LM Studio benchmark identity includes the selected CLI revision, desktop-app version, and a deterministic digest of the installed MLX runtime-pack set. Its MTP capability additionally requires an audited sidecar and a side-effect-free local CLI-help probe for enable, disable, maximum-draft, minimum-draft, and continuation-probability flags. An app, pack, CLI, or artifact change therefore fails closed instead of inheriting stale evidence.
- Benchmark comparison contract v4 records canonical settings for every measured mode plus the fixed engine controls that shaped the route. LM Studio MTP identity is exactly maximum draft size, minimum draft size, and a finite 0.01-step continuation-probability cutoff; minimum cannot exceed maximum. The fixed identity also captures oMLX batching, LM Studio GPU/parallel controls, or MTPLX profile/fan policy, so applying a winner restores the measured setup. Older LM Studio records that captured only the winning maximum depth cannot drive the optimiser.
- The LM Studio MTP tuning worker uses a versioned bounded-coordinate plan: one AR reference, then at most ten deduplicated MTP candidates across maximum, cutoff, and minimum stages. Every candidate is a fresh load with greedy parity and a matching resource-start gate. Only the complete selected candidate is promoted into ordinary v3 AR/MTP evidence; cancellation, failure, or environmental mismatch commits nothing, and the sweep manifest is revalidated before the optimiser can consume it.
- Cross-engine Calibration embeds each engine-owned bounded search inside the matrix. LM Studio evaluates AR plus at most ten deduplicated MTP candidates across maximum draft size, minimum draft size, and continuation cutoff; oMLX evaluates AR, available native MTP, and at most ten DFlash candidates across block size, verifier, and draft precision; MTPLX expands MTP into every artifact-verified depth from D1 through `depthMax` (at most eight). Every candidate uses the same generated schedule, AR correctness reference, cooling/runtime identity, and shared resource-start gate. The plan exposes worst-case reload/request counts, the UI labels them as upper bounds, and only each engine's fastest correctness-clearing candidate enters the final cross-engine matrix. Complete sweep manifests are stored and revalidated so the optimiser restores the exact measured settings.
- DFlash tuning has a separate versioned bounded-coordinate plan tied to the exact target/draft fingerprint and the still-selected recommended oMLX build. It searches at most ten deduplicated candidates across block size, verifier, and draft precision. AR and available native MTP are retained as final competitors. Every candidate has a fresh load, greedy parity, and matching resource-start gate; the selected DFlash identity and complete sweep manifest must revalidate before any result can guide the optimiser. Cancellation, runtime/pair drift, failure, or environmental mismatch commits nothing.
- Route checks never open a work surface, read project content, or retain generated response text, and their temporary model allocation is stopped through the normal ownership boundary.

The next sensible extraction, if the launcher grows beyond the current adapters, is to move each builder into a small module while keeping these registries and contracts stable. Dynamic third-party adapter loading should wait until there is a signed package, permission, versioning, and sandbox story.
