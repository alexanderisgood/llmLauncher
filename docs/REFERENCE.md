# LLM Launcher reference

A capability-aware hub for running models through local **oMLX**, **LM Studio**, or **MTPLX**, plus optional **SwiftLM** and **Mference** SSD-streaming routes for verified oversized MoEs, then opening each compatible route in **Pi**, **OpenCode**, **Codex**, or a built-in streaming **Chat**. The implemented native/connected **FreeToken** integration is temporarily hidden behind one off-by-default UI feature flag while that route matures; its backend, saved data, and tests remain intact.

## Start

Double-click `Start LLM Launcher.command`. It selects the first available Python 3.10+ interpreter (an explicit `LLM_LAUNCHER_PYTHON`, then common Homebrew/python.org locations) instead of Apple’s incompatible Python 3.9. The launcher opens a local page at `127.0.0.1`; it is not hosted on the internet. Opening it again reuses the verified controller already holding the owner-only instance lock and brings that page forward instead of starting a second state writer.

The browser remembers the last usable engine, model, and work surface shown in the launcher. On the next start it restores that exact route only if the runtime, artifact, and surface are still available; otherwise it chooses the first installed compatible route and uses built-in Chat when no compatible agent is installed. This selection starts nothing and does not restore or change context, response limits, reasoning, sampling, KV precision, accelerator controls, prompts, or folders.

1. Optionally open **Models** to search every detected artifact and see its compatibility doctor: installed engines, decode modes, work surfaces, and matching saved evidence. Selecting a model/engine here changes only the visible launcher choice.
2. To add a model, choose **Find / download a model** inside Model Library. Search or inspect one public Hugging Face repository, review the pinned commit, license, exact MLX/GGUF file set, destination, disk and memory checks, then explicitly approve the resumable download. Search and inspection create nothing.
3. Choose oMLX, LM Studio, or MTPLX. A supported MoE whose weights do not fit safely in memory can instead use **Huge models on SSD** with SwiftLM or Mference. FreeToken is deliberately absent from the current interface; enabling its single UI flag restores the already-implemented native and connected routes.
4. Optionally open **Tools → Runtimes** to inspect the exact oMLX, LM Studio, and MTPLX executables used by new local sessions. Opening it is local and read-only; switching to another already-installed copy is explicit.
5. In the default **Focused** view, a quiet collapsed **Saved routes** strip can reveal at most one ready launch profile, one Session Set, and one resumable Chat. It never replaces or disables the normal configuration form or Launch dock. Profile launches still revalidate current models, runtimes, measurements, memory, and exceptional approvals; a Session Set still opens its side-effect-free review plan. Open **Tools → Launch profiles** to save or manage the full visible launch setup.
6. Once a normal model session has the agents and Chats you want, optionally open **Tools → Session sets** and save them together as one **Session Set**. Reopening first shows a side-effect-free plan, then its action button loads one model or reuses the exact resident route and opens only the missing surfaces. A separate checkbox appears only for a current memory-risk acknowledgement or experimental route.
7. Choose a compatible detected model.
8. Choose Pi, OpenCode, Codex, or Chat and enter the working folder. For an agent, choose launcher-owned **Hub Console** or the external macOS Terminal fallback.
9. Keep or change context, maximum response, reasoning, and supported advanced controls. A verified LM Studio MTP route exposes maximum draft size, minimum accepted draft size, and the probability cutoff for continuing a draft. Chat also exposes a system prompt and model-default or custom temperature, top P, top K, presence penalty, frequency penalty, and seed.
10. Optionally open **Sessions** to inspect the launcher-owned route, live request scheduler, Cache Observatory, and a conservative full-context capacity estimate for the next launch. Once a normal route is running, Sessions—or the main Launch button when every engine control matches—can attach another compatible Pi, OpenCode, Codex, or Chat surface without loading the weights again. Active and waiting requests can be cancelled individually. An optional session-only idle timeout unloads launcher-owned oMLX, MTPLX, or native FreeToken; a connected FreeToken route closes only its private Mac-side bridge and leaves the server model untouched.
11. Optionally open **Tools → Calibration**. Its first screen is read-only: Focused mode shows the workload, goal, cooling, and one Result area; Full details adds the locked contract, included engines, reloads, and generated request count. When an explicit reasoning level would exclude an otherwise compatible engine whose benchmark route exposes only model-default reasoning, Calibration normalises every engine to model default and labels that change. Existing matching evidence can be used immediately; otherwise **Test engines** starts the visible plan without a redundant checkbox.
12. For a compatible DFlash 2 target, optionally open **Setup Assistant** to review the runtime, pinned draft revision, exact destination, and disk headroom. Nothing changes until the separate consent box is checked and Download is pressed.
13. Optionally choose **Show details**, then open **Benchmark Lab**. **Current engine only** measures AR against that engine's verified accelerators. A verified LM Studio MTP route offers **Run bounded MTP tune** for maximum draft size, minimum draft size, and continuation cutoff; a verified oMLX DFlash 2 route offers **Run bounded DFlash tune** for block size, verifier, and draft precision. **Compare all engines** runs one locked contract across every compatible installed engine, including AR-only engines. Shootouts rotate which engine goes first and wait for comparable Mac conditions before every route. The same matrix can rank generation TPS, total speed, first-response latency, unified-memory pressure, or thermal stability, while Measurement history shows like-for-like changes across repeated runs.
14. For an eligible dense Qwen checkpoint, optionally open **ANE Tuner**. It measures a GPU baseline and temporary ANE/GPU splits in a private oMLX process; approximate ANE prefill remains off until a positively traced result is explicitly selected.
15. Read the compact performance receipt beside **Apply fastest safe settings**. It checks the selected model, work surface, intelligence, sampling, limits, KV precision, workload, runtime build, and Mac against strict local history. A fresh exact winner offers **Apply**; old evidence offers **Rerun**; a tie offers **Review**; and missing evidence offers the appropriate Calibration or Benchmark Lab route. The main button optimises the current engine, while its arrow menu also exposes engine goals. **Verified quick launch** continues from a measured fastest-engine decision into Route Check and, only after that exact route passes and unloads, enables one checked launch.
16. Optionally press **Check route**. Its first screen is read-only. **Run Route Check** loads the exact selected model once, sends one generated streaming request plus a harmless tool-schema request for agent surfaces, reports protocol/streaming/tools/usage/reasoning separately, opens no work surface, stores no generated text, and unloads automatically.
17. Press the single **Launch** button. It always uses exactly the settings currently shown. With no active route it performs the normal model load. With an exact matching resident engine contract it becomes **Open warm chat/Open Pi/OpenCode/Codex** and adds only that work surface—zero model reloads. Agents default to the in-launcher Hub Console, with one activity/unread tab per attached agent plus bounded find and copy controls; macOS Terminal remains an explicit fallback. Chat stays inside the launcher, separates runtime-emitted thinking from the final answer, lets you scroll through earlier messages without a live stream pulling you back down, queues messages typed during generation, keeps a persistent conversation sidebar, recovers unfinished drafts and paused queues after a refresh, and shows authoritative token/cache usage when the runtime supplies it.

The full guide is in `manual.html` and is also linked from **Tools → Manual**.

Use polished light **Frost**, **Graphite**, light **Daylight**, **Ember**, or **Midnight** from the top-bar appearance menu at any time. Frost uses a unified app toolbar, edge-to-edge content split, restrained translucent materials, native blue controls, quieter shadows, and one shared height/baseline system for adjacent header, dock, Chat, and dialog controls. Graphite remains the neutral default; Daylight is the original true-light workspace; Midnight preserves the original blue/violet look. Hub Console is the deliberate exception: its complete workspace—tabs, status, terminal, and composer—remains black with one stable high-contrast ANSI palette in every appearance. The same menu controls information level. **Focused** is the default: a usable saved route adds only a compact, collapsed Saved routes strip above the normal form. Expanding it never hides or disables the settings form or Launch dock. Profile launches rerun the ordinary validator and Session Sets still require their exact review plan. Focused gives Launch configuration the full workspace width, keeps the three current engines on one scan-friendly desktop row, and replaces the mostly empty inspector column with one compact live strip beside the heading. Exact phase and status remain visible there, with Stop and Log controls available whenever their full-inspector equivalents are available. Narrow windows return the engines to two columns automatically. It also keeps model, work surface, limits, a plain-language performance receipt, optimisation, Launch, Chat history/search, TPS, thinking, and errors visible while moving repeated help, evidence cards, inventory, Route Check, and Preview out of the primary scan path. Hub Console similarly keeps agent/model, authoritative speed, request lane, failures, and controls visible in one compact expandable strip; Details reveals its exact route, first-output time, and full lane report. When an exact cross-engine result exists, the winning runtime card receives a small **Best** badge; when Chat uses model-default sampling, inactive override fields disappear until **Custom** is chosen. Calibration follows the same rule: its compact view keeps the exact route summary, engine eligibility/exclusions, measurement cost, warnings, and progress, while **Full details** reveals the eight-field contract and accelerator badges in place. **Show details** or **Detailed** restores the full right-hand inspector and everything else globally. Palette and information level are applied before the interface paints and store only those two presentation names in this browser; neither can change a model, runtime, profile, benchmark, launch setting, or chat.

## Safety contract

- Existing Pi, OpenCode, Codex, oMLX, LM Studio, and MTPLX configuration files are never rewritten.
- Startup holds one owner-only controller lock per macOS user. A second launch opens the first controller only after its loopback status identifies itself as LLM Launcher; it cannot create another server or race the same state files. Signal shutdown stops owned work before releasing that lock.
- The controller records the exact launcher source stamp when it starts. If the Python file changes while that process is still resident, the page reports that a restart is needed and every operation that could start a model, measurement, download, runtime change, or Session Set fails before doing work. Stop and cancellation paths remain available.
- The last-visible-route browser preference contains only an engine ID, model ID, and work-surface ID. It is schema-validated against the current installed route catalog before use, stores no path, prompt, setting, credential, or benchmark claim, and cannot start a model or client.
- Model Library scanning is read-only. It derives its report from the canonical model scanner, adapter registry, compatibility matrix, installed-command status, and already-saved local evidence; it never starts an engine, loads or downloads a model, uses the network, or modifies an artifact.
- Model Acquisition search and inspection are explicit anonymous public-Hub requests and never use an implicit Hugging Face account token. Acquisition accepts only public standard MLX checkpoints or one exact GGUF variant, pins the repository to an immutable commit, requires a separate license/repository review, writes only beneath a fixed known model root, preserves partial files for resume, verifies exact sizes and available LFS SHA-256 checksums, and starts no downloaded code or runtime. Existing unowned folders, gated/private models, unsafe files, custom-code repositories, and standalone draft components fail closed.
- Launch profiles store only the validated visible settings contract in an owner-readable launcher file. They never store chat turns, responses, runtime credentials, assigned ports, generated secrets, or an experimental FreeToken approval. Auto-measured profiles recheck current evidence and keep their saved engine when the matrix is incomplete or tied. The collapsed Saved routes strip displays only the first currently ready visible profile and calls the ordinary profile launch path.
- Session Sets store one validated shared model contract plus bounded per-surface choices in an owner-readable launcher file. They never store Chat messages, terminal or Hub Console output, credentials, ports, running-process state, generated secrets, or experimental-run approval. Planning is side-effect free; opening rebuilds the exact contract under the normal operation lock, requires an exact confirmation (plus current memory or synthetic-only FreeToken approval when applicable), starts at most one model route, and delegates every additional surface to the ordinary attachment validator. The Saved routes strip displays only the first currently ready visible set and opens its normal review dialog; it never approves the plan. External Terminal handoffs are never claimed already open because the launcher cannot observe their lifetime.
- Calibration planning is local, read-only, and side-effect free. Pressing its clearly labelled Run button starts the exact displayed measurement, which uses generated prompts instead of project data, runs one isolated route at a time through the normal resource gates, and never promotes a stopped or incomplete matrix. LM Studio is not labelled as having “no reasoning”: its common Chat Completions benchmark route is model-controlled. If that single mode is the only reasoning mismatch, Calibration visibly normalises all included engines to model-default reasoning; measuring changes no launch control, and applying that result explicitly changes the visible reasoning setting to the measured common mode.
- Sessions & capacity inspects only launcher-owned process references and Apple's public system-wide headroom/thermal state. Its estimate is conservative rather than a claim of exact RSS or GPU allocation. A tight, unknown, or over-headroom plan needs a one-time acknowledgement bound to the exact visible contract; Launch resamples and revalidates it. Attaching a surface inherits the active model/context/output/reasoning/runtime contract and builds only a per-surface overlay.
- Every launcher-created surface in a normal session receives a distinct bearer key for one private loopback relay. Generation admission is bounded and first-come, first-served using the exact engine lane count: one for current oMLX/MTPLX launch contracts and the visible parallel count for LM Studio. Sessions exposes request IDs, surface/protocol labels, queue position, timings, byte counts, result state, and runtime-reported token counts/speeds only; it stores no prompt, response, reasoning, tool, file, project, or credential content. Independent clients that know the engine port remain outside this claim.
- Hub Console owns only the exact Pi/OpenCode/Codex process started for that surface. Input and resize use authenticated local controller calls; each agent's terminal output is capped at 2 MiB in process memory, is never written to Chat History or a console log, and disappears with the launcher process. Refresh reconstruction reads that bounded backend buffer again; `sessionStorage` keeps only the active surface ID, visibility flag, and numeric seen offsets, never terminal text. It may contain whatever the agent prints, including project material, so the Terminal fallback remains available for workflows needing fuller VT compatibility or a separate window. Stopping an agent leaves its shared model route loaded; stopping the route ends every owned Hub Console before closing the relay and engine. Terminal handoffs remain external and are never adopted or terminated.
- Warm-route planning is side-effect free and binds the active run ID to the canonical engine, model fingerprint, context, response limit, reasoning, and every engine option. Project, agent choice, and Chat prompt/sampling are per-surface overlays. The backend rebuilds this contract before attaching; a stale confirmation or changed engine control fails closed. “Engine resident” never implies that a later prompt prefix will hit cache.
- Cache Observatory keeps at most 64 numeric observations in memory for the current session. It covers only built-in Chat usage parsed by the controller, never stores prompts, answers, reasoning, files, projects, or keys, and disappears when the route stops. A cache hit is confirmed only from runtime-reported cached-token fields; lower latency alone is not relabelled as reuse. Pi/OpenCode/Codex requests are labelled by the private relay for scheduling, but their response bodies are deliberately not parsed into Cache Observatory.
- Runtime and client receive the same context and output limits.
- LM Studio model discovery resolves the canonical default identifier from its local side-effect-free model index before building `lms load`. This handles aliases such as `model@6bit` that differ from the case-preserved Hub folder. Malformed or out-of-catalog index entries are ignored, and a stale catalog rejection asks the user to open LM Studio once and Rescan rather than mislabelling the failure as reasoning incompatibility.
- Route Check planning is side-effect free. Pressing **Run Route Check** starts the exact displayed check, which uses only fixed synthetic prompts, caps each response at 64 tokens, probes the actual Chat Completions or guarded Responses route, and stops the temporary model before reporting cleanup complete. It never opens Pi, OpenCode, Codex, or Chat, reads project files, stores generated text, or treats absent usage/reasoning as invented evidence. Agent tool-schema rejection fails the route; a model choosing text after accepting the schema is an advisory.
- Verified Quick Launch issues a memory-only, ten-minute checked-launch receipt only after Route Check passes or advises and its temporary route is fully unloaded. The receipt is bound to the exact visible contract, model fingerprint, runtime version and executable revision, and adapter schema. Launch recomputes and validates that identity inside the backend launch lock; a changed setting, model, runtime, expired receipt, failed cleanup, or launcher restart requires another check.
- Built-in chat turns are accepted only for the exact active route and Chat attachment. The controller prepends the locked system prompt, enforces the selected response ceiling, and keeps runtime API keys out of the page. Context Pack files and Workspace Context folders must be explicitly selected in the browser; the backend accepts only bounded named text, never a filesystem path, labels every body as untrusted reference data, and excludes it from History. Workspace indexing blocks common generated paths and likely credential files before retrieval. Conversation history is a separate owner-readable local file; it stores messages, optional visible-turn timestamps, started/latest route metadata, a settings-only cold-resume contract, and only reasoning text actually emitted by the runtime. The resume contract may retain the selected project folder but never the system-prompt text, credentials, project-file contents, Context Pack/Workspace bodies, assigned ports, or unavailable hidden reasoning; a required prompt must be re-entered or explicitly omitted. Legacy chats without the versioned contract remain readable but cannot cold-resume. Current-transcript search remains page-memory-only. Unfinished composer text and waiting-message text use separate bounded browser-tab recovery stores. Neither contains attachments, workspace indexes, system prompts, credentials, responses, or runtime state.
- The optimiser preserves model weights, quantisation, context, response limit, reasoning, sampling, prompts, tools, KV precision, and the visible cooling choice. It cannot promote an MTPLX route to maximum fans.
- “Use highest-TPS engine” requires matching records for every compatible installed engine: same Mac, model fingerprint, workload suite, client, context/output limits, reasoning, sampling, KV precision, and generated-input schedule. An incomplete matrix or a generation lead below 3% keeps the current engine.
- “Fastest safe” means the best supported setting backed by the evidence currently available for this Mac and artifact. It is not a claim that one speculative method wins every prompt length and workload.
- Benchmark Lab uses generated text rather than project data, reloads and isolates every route, and requires authoritative runtime token counts. Exact deterministic parity remains mandatory between AR and speculative modes inside one engine. Cross-engine comparison instead binds the same model, inputs, settings, and sample schedule, then allows tightly bounded tokenizer/terminal-token drift while surfacing different output fingerprints as a warning; materially different work still blocks a winner. Its v4 evidence contract records both the load-time settings for every measured mode and the fixed controls that shaped the route: oMLX batching, LM Studio GPU/parallel settings, or MTPLX profile/fan policy. Engine Shootout rotates first-engine order and applies one shared, bounded resource-stabilisation gate before every route. Passing routes are not rejected later by a stricter pairwise headroom test. Automatic/System controlled cooling may still let macOS raise its fans under sustained compute. Cancelled or failed shootouts never save a partial matrix.
- Runtime Promotion measures an installed checksum-verified oMLX candidate against the currently selected copy without changing `BINARIES` or runtime preferences. It binds both executable byte revisions, the exact model fingerprint, Mac, workload, reasoning, sampling, context, and output contract; forces cache-isolated AR, full-precision KV, and no ANE tuning; and alternates first-run order across matching repeats. Promotion is withheld unless deterministic output and token counts match, both public memory/thermal/power starts are comparable, median and worst paired speedups both reach 3%, peak pressure regresses by no more than 512 MiB, and thermal state does not worsen. Complete evidence contains metrics but no prompts or generated text; stopped and failed comparisons save nothing, and a trusted result still needs a separate explicit Promote action within seven days.
- Setup Assistant is read-only until explicit consent. Its DFlash 2 action downloads one public repository at a pinned commit, preserves partial files for resume, and strictly validates the result. It never installs or replaces oMLX, edits an agent configuration, deletes a model, or modifies existing weights.
- ANE Tuner is fail-closed. It requires oMLX 0.6.3rc2+, a native Qwen prefill kernel whose upstream self-check passes, a dense Qwen affine 4/5/6/8-bit group-size 64/128 checkpoint, checkpoint weights plus an 8 GiB capacity reserve, and a profiler log proving positive ANE operations. Results are bound to the exact checkpoint/runtime/Mac. CPU sharing is an advanced, default-off candidate pool available only when bounded safetensors inspection proves a separate all-FP16 clone, a 16 GiB reserve fits, and the resulting CPU fractions stay inside the upstream tuner grid. The consent-gated clone assistant validates every source shard before writing, converts only BF16 floating tensors in a unique staging folder, preserves packed integer weights, and promotes the new sibling directory only after complete verification; the original is read-only throughout. No partial, untraced, or mismatched result can be launched.
- Quantised KV, unverified DFlash/DFlash 2, and unverified MTP remain manual or disabled.
- Dedicated oMLX/MTPLX/native-FreeToken processes are stopped only by their recorded process group. LM Studio's shared server is left running; only the launcher's unique model identifier is unloaded. Connected FreeToken Stop and idle timeout close only the launcher-owned loopback bridge; they never stop or unload the remote server.
- Local engines bind to `127.0.0.1`, use private per-run settings, and open a work surface only after the exact selected model appears at `/v1/models`. Native FreeToken is additionally started with offline/local-files-only policy and its versioned `/health` contract is revalidated after launch. A connected FreeToken upstream may be remote, but every Pi/OpenCode/Codex/Chat surface still receives only its own authenticated `127.0.0.1` bridge.
- Codex uses native `/v1/responses` on oMLX and LM Studio. For MTPLX, the private launcher relay supplies a fail-closed Responses bridge over `/v1/chat/completions`: standard functions and Codex namespace children are mapped reversibly, hosted web search is disabled for the fully local route, and an unknown future tool or input shape is rejected before inference.
- Normal Chat, Pi, OpenCode, and Codex traffic passes through the session's private loopback relay. The relay caps Chat output and applies the Codex Responses/reasoning contract even when the client omits `max_output_tokens`; the upstream runtime key never reaches a work surface.
- Remote FreeToken discovery is performed only after **Connect & discover**. The endpoint rejects embedded credentials, queries, fragments, link-local, multicast, and unspecified addresses; redirects are disabled; HTTPS certificates are verified; the upstream key is kept in an owner-only launcher file and is never returned to the page or handed to an agent. Ordinary Model Library refresh then reuses only the last explicitly discovered remote catalog. Native FreeToken scanning is local and side-effect free: it accepts only the exact versioned port schema, Qwen3-MoE architecture, local-files-only security contract, supported working set, and internally consistent runtime-owned qualification evidence. Synthetic-only compatibility stays amber and consent-gated. The native greedy-only milestone and connected routes remain outside cross-engine Benchmark Lab; authoritative live TPS stays visible.

Generated runtime files, logs, and the bounded `chat-history.json` store live under `~/Library/Application Support/LLM Launcher`.

## Adapter architecture

Engines and work surfaces now have one canonical registered descriptor, one compatibility policy, and one dedicated builder. Unknown adapters fail explicitly instead of falling through to another runtime, and the launcher checks at startup that every descriptor has a builder and a complete compatibility row. The interface receives the same read-only catalog through bootstrap for labels, executable mappings, protocol, built-in status, and installation state.

This is an internal extension seam, not arbitrary plugin loading. Adding an engine or work surface still requires reviewed code and tests, which keeps generated commands, temporary overlays, credentials, and the no-global-config-write guarantee auditable. See [`ARCHITECTURE.md`](../ARCHITECTURE.md) for the flow, builder contract, and contributor checklist.

## Oversized MoEs on SSD

**Huge models on SSD** is an optional, collapsed runtime lane rather than a fourth ordinary in-memory choice. [SwiftLM](https://github.com/SharpAI/SwiftLM) consumes supported MLX MoEs and streams routed experts from SSD. [Mference](https://github.com/NeelM0906/Mference) is model-specific and accepts only its verified pinned `.gturbo` repacks. Both can serve Pi, OpenCode, and built-in Chat through Chat Completions; neither currently supplies the Responses endpoint required by Codex.

The scanner first proves that the artifact is a complete MoE, records its full weight size relative to installed memory, and reads the checkpoint's native expert top-k. SwiftLM includes the Qwen3-Next family named by its current upstream release. Mference additionally requires bounded regular metadata, `GTURBO` v1, known flags, one of its pinned streaming architecture signatures, an install receipt bound to the exact directory and manifest hash, the same declared file set/sizes/hashes, safe regular paths, and every non-empty expert-layer payload. The SSD lane is recommended when the weights reach 85% of installed unified memory, remains optional for a smaller supported MoE, and stays unavailable for an unknown architecture. The launch builders preserve native expert routing and do not enable speculative decoding: on an SSD-bound path, multiplying verification-time expert reads can reduce rather than improve throughput.

SwiftLM exposes only a bounded prompt-prefill chunk choice plus the read-only native top-k. Mference exposes its prompt-cache policy, queue limit, and six fixed context windows from 4,096 through 128,000 tokens. Direct launches reject another value before starting the server and pass the launcher's exact served model ID. SSD Calibration visibly selects the largest common supported context at or below the request and applies that context with the result, so the subsequent fastest-engine action matches the saved evidence. Runtime installation and model-specific conversion remain upstream operations; the launcher discovers installed binaries and verified artifacts but does not silently download, repack, or execute an unsupported model.

When both runtimes have artifacts derived from the same immutable repository and revision, Calibration can compare them as one source-bound pair. A matching filename is not enough: MLX metadata or a launcher-verified `.gturbo` receipt must produce the same cryptographic comparison identity. Each route starts in a fresh process and runs separate first-turn and warm-prefix stages using generated agentic prompts. The result records generation TPS, TTFT, memory pressure, thermal state, prefix reuse, natural cold-to-warm cache state, and exact runtime/artifact identities. macOS file cache is observed rather than forcibly purged.

[Qwen3.8-Flash-Next](https://github.com/QwenLM/Qwen3.8-Flash-Next) is a new 125B MoE with a changed QSA/GDN architecture. The launcher recognises it as an SSD-streaming candidate but currently marks both routes incompatible: SwiftLM does not list the family in its accepted architectures, and Mference has no pinned `.gturbo` implementation for it. This is a deliberate fail-closed boundary, not a claim that the model can never be ported.

## FreeToken: native port or connected engine

> **Temporarily UI-hidden.** Version 1.66 keeps this implementation, its saved records, bridge, native-port validation, and tests, but removes it from runtime choices, tool inventory, Model Library, calibration, Saved routes, profiles, Session Sets, and cold-resume actions. Set `UI_FEATURES.freetoken` to `true` in `app.js` to restore the interface after the route is ready for normal use. Existing FreeToken transcripts remain readable and their saved route data is not deleted.

The launcher automatically checks the sibling `../freetokenport` environment and standard command locations for the experimental Apple-Silicon port. It never imports or executes model code while scanning. A local checkpoint becomes selectable only when `ft macos-inspect --json` returns the exact `freetoken.native-macos-capabilities` v1 / native API 1.0 contract, local-files-only security, a complete Qwen3-MoE model, a supported working set, and a valid schema-v1 qualification receipt. A rejected checkpoint stays visible through its compatibility reason; when the port is present but no checkpoint passes bounded preflight, the launcher says exactly that.

Compatibility is not presented as production qualification. The current port proves a tiny synthetic checkpoint path but has not qualified a real large checkpoint. The launcher therefore labels a matching existing model **Experimental · synthetic path only**, never turns that state into a download prompt, and requires one model-bound checkbox before Preview or Launch. The backend independently requires the same approval. A future green qualified state is accepted only when runtime-owned evidence binds the exact local path, model identity, immutable revision, SHA-256 checkpoint fingerprint, architecture, weight size, quantisation, runtime/API versions, successful server start, and successful real-weight token generation. Missing, malformed, forged, changed, or internally inconsistent evidence fails closed.

Native launch is deliberately narrow today: built-in Chat Completions and streaming only, greedy decoding only, no tools, and no Responses API. The launcher exposes active sequences, resident/hot expert placement, and exact-prefix-cache entries; it rejects the port's unsupported batching-plus-prefix-cache combination. It force-runs preflight again before starting `ft macos-serve`, binds only to `127.0.0.1`, disables network downloads and remote code, verifies the exact checkpoint/binary/qualification/live-health identity, never enables the unsafe working-set override, and owns the process. Normal Stop or idle timeout therefore unloads native FreeToken.

The official [FreeToken installation requirements](https://github.com/FlashML-org/FreeToken/blob/main/docs/install.md) still describe the upstream Linux x86_64/NVIDIA/CUDA 13 implementation; this separate MLX/Metal port does not change that upstream platform claim. The native greedy-only route stays outside Calibration and cross-engine Benchmark Lab until it can preserve the same sampling contract; built-in Chat reports live local prefill and generation TPS instead.

When the UI flag is re-enabled, a connected route can be configured through **FreeToken → Remote server settings** with the server origin (or its `/v1` base), optional API key, and context limit. Returned model IDs appear beside native models. Pi, OpenCode, and Chat use Chat Completions while Codex uses Responses, subject to the server's advertised contract. Each surface talks to a launcher-owned authenticated loopback bridge, never directly to the upstream address. Stop closes that bridge only—the server and loaded model remain owned by its operator. Connected performance also stays out of the Mac-only benchmark matrix because host hardware, network latency, and other users are not comparable; live server-supplied TPS is the truthful signal.

## Model Library

Open **Models** for a searchable inventory of every detected local target artifact across the three visible engines. The hidden FreeToken-only remote catalog is retained by the backend but omitted from cards, counts, filters, and actions. Each visible card separates artifact compatibility from runtime installation: it can explain that a checkpoint fits oMLX even when oMLX is missing, while only marking a route ready when the engine, model, work surface, protocol policy, and enforceable reasoning controls all agree. Choosing one engine in the filter keeps incompatible checkpoints visible, scopes every badge/count/diagnosis to that engine, and hides the other engine cards.

The compatibility doctor reports artifact completeness, installed loadable engines, ready engine/surface combinations, AR/MTP/DFlash 2/locally verified ANE modes, and matching saved benchmark history. A missing accelerator is an advisory rather than a broken model because ordinary AR decoding remains valid. An available accelerator with no matching measurement is also advisory; availability alone is not presented as proof of speed.

**Use with …** selects that visible engine and model in the normal launcher without starting anything. The current Pi/OpenCode/Codex/Chat choice is deliberately preserved, so an unsupported combination remains visibly blocked instead of being silently changed. Refresh scans only the documented local roots and installed commands; it does not contact model hubs, runtime update services, or the hidden FreeToken server route.

## Model Acquisition Center

Choose **Find / download a model** from Model Library to open a deliberately separate public-network workflow. Opening the center performs only a local status check. Search sends the entered text to the public Hugging Face Hub; direct inspection sends one public repository ID and optional revision. Both run with implicit Hub authentication disabled, so saved account tokens are neither used nor exposed. Gated and private repositories are outside this path.

Inspection resolves a branch or tag to an immutable commit, reads the pinned file tree, and builds a side-effect-free plan. A standard MLX checkpoint must include root metadata and a complete safetensors weight set. A GGUF repository exposes each single quantisation or complete shard group as a separate choice; it never turns “download this model” into “download every quantisation.” Draft-only components such as the DFlash 2 draft and repositories containing custom root code are blocked as standalone chat targets. The dedicated Setup Assistant remains the correct paired path for DFlash 2.

The plan shows the license, full commit, exact files and available LFS checksums, selected destination, existing/resumable bytes, free-space admission with a 4 GiB reserve, a conservative weights-plus-8-GiB memory advisory, and expected engines. Expected compatibility is not a speed claim. Download remains disabled until the model page/license checkbox is selected, and the approval is bound to the exact `repository@commit`, variant, and destination for 30 minutes.

An approved download invokes the installed Hugging Face CLI with explicit filenames, the pinned revision, a fixed known local directory, and at most four workers. Stop preserves completed files and Hub metadata for resume. Completion still requires exact sizes, every available LFS SHA-256 checksum, and MLX safetensors structure/completeness or GGUF magic validation. Only then does **Open Model Library** rescan the artifact and expose real engine/surface routes. Benchmark Lab remains the authority for the fastest engine on this Mac. These behaviours follow Hugging Face's documented [`--revision`, `--local-dir`, and resumable local metadata](https://huggingface.co/docs/huggingface_hub/en/guides/cli) and [download/dry-run model](https://huggingface.co/docs/huggingface_hub/guides/download).

## Sessions & capacity

Open **Sessions** to see the current launcher-owned model route, its owned engine/private-relay processes, and every Pi/OpenCode/Codex Hub Console or Terminal handoff plus built-in Chat. The launcher deliberately runs at most one owned model allocation at a time, but that allocation can serve up to 12 work surfaces. It never adopts or terminates an external runtime, and an LM Studio session owns only its uniquely named loaded-model slot—the shared LM Studio service remains outside the stop boundary.

While a normal route is Running, choose another work surface under **Reuse the loaded model**. The side-effect-free preview proves that the engine, weights, model ID, context, output ceiling, reasoning, KV mode, acceleration, and relay stay fixed. Pi and OpenCode receive temporary per-run provider overlays; Chat receives its own system prompt and sampling controls; every surface receives a different relay key. Codex uses the same relay's bounded native Responses path on oMLX or LM Studio and its tested Responses-to-Chat bridge on MTPLX, so it can attach without reloading the weights.

The main Launch button now uses the same rule. It offers a warm open only when the visible backend, checkpoint fingerprint, context, response ceiling, reasoning, KV precision, and all engine controls exactly match the running route and the chosen surface remains compatible. The backend revalidates a run-bound confirmation immediately before attaching. A mismatch names the changed controls and keeps Launch disabled until the route is stopped or the visible contract matches again. Changing the project, agent, Chat system prompt, or Chat sampling is allowed because those values belong to the new surface rather than the resident engine.

**Cache Observatory** deliberately separates three facts: the model is resident, that engine's cache policy is configured or engine-managed, and a particular prompt prefix was actually reported reused. oMLX normal sessions use launcher-enabled memory plus a bounded 40 GB SSD tier; MTPLX normal sessions explicitly enable its SSD session cache; LM Studio owns its cache lifecycle. Per-turn hit counts, reported cached tokens, token reuse rate, and hit/miss first-output medians appear only for controller-relayed built-in Chat. Missing cache telemetry remains unavailable, and timing never becomes fabricated hit evidence. These observations are bounded to 64, live only in memory, and clear with the session.

**Live request scheduler** shows the engine's real launcher-controlled work rather than guessing from open windows. Each active or queued generation has a random request ID, surface and protocol label, wait/run/first-output timing, and a Cancel action. oMLX 0.6.3rc2+ can add live prefill or generation TPS, prompt progress, context/generated-token counts, and numeric stall age through its protected local activity endpoint. The launcher creates one transient controller-only admin session with the already-private engine key; that cookie is never sent to the page or persisted. MTPLX 2.9.1+ can similarly report the active prefill/decoding phase, live TPS, context/generated-token counts, MTP acceptance by depth, and a numeric stall age. Either engine summary is attached only when exactly one private-relay request and one exact-model engine record are active and their elapsed timing agrees; ambiguity fails closed. After completion the scheduler shows decode TPS and end-to-end TPS only when the runtime reports authoritative prompt/output token counts. Decode TPS is `(output tokens − 1) ÷ time after first output`; end-to-end TPS is `output tokens ÷ total admitted request time`. LM Studio response `stats`, when present, take priority for exact engine-reported TPS and can add numeric MTP draft acceptance; missing or malformed fields fall back to the usage-plus-relay calculation. Neither path estimates from text, so unsupported runtimes display **TPS unavailable**. LM Studio remains completion-only because its shared service exposes no safely attributable per-request live counter to this launcher. Admission is FCFS and bounded to 64 waiting requests. Current oMLX and MTPLX sessions use one lane; LM Studio uses the exact parallel count selected at load. Completed metadata is capped at 32 rows and disappears with the relay. Prompt text, response text, reasoning text, tools, and project data never enter this registry. Engine request/session/model IDs, draft-model IDs, recorder paths/history, generated-text tails, and unrelated loaded-model records are discarded rather than published or persisted.

**Unload after idle** is off by default and belongs only to the current session. For oMLX and MTPLX, a 5–120 minute timeout counts only while no relayed request is active or waiting, then stops the launcher-owned route through normal cleanup. It is disabled for LM Studio because that shared unauthenticated loopback service may have direct clients the launcher cannot see; unloading based only on relay silence would be unsafe.

An agent can use **Hub Console** or **macOS Terminal**. Hub Console is launcher-owned: every attached Pi/OpenCode/Codex process gets a keyboard-accessible tab with generating, queue, stopped, failure, and unread-output state. Pi uses its supported RPC embedding mode here: the Hub restores the current Pi session messages, appends new user, thinking, response, tool, and queue events instead of displaying a self-erasing TUI screen, changes Send to Queue while Pi is responding, and exposes Clear queue and Stop response. Follow-ups wait in a bounded launcher-owned queue and are submitted one at a time, so Clear queue works on the installed Pi 0.84.2 as well as builds with newer queue commands. Confirm/select/input/editor requests from Pi extensions appear as ID-bound inline cards; answering or cancelling sends only the matching RPC response. A bounded state probe repairs a missed settle event after acknowledged prompt preflight, a final JSON record is consumed even without a trailing newline, and terminal row changes move displaced content through bounded scrollback rather than clipping the newest answer. Model/tool control bytes are made printable before the launcher adds trusted colour headings, so generated text cannot clear earlier output. Use Terminal when you want Pi's complete native TUI. OpenCode and Codex Hub tabs retain direct keys, paste, and resize. Switching tabs keeps each pending message, command, or keystroke bound to its original process. In Focused presentation, one expandable status strip keeps the active agent/engine/model, authoritative TPS, request lane, and any process failure visible without taking transcript space. oMLX 0.6.3rc2+ can distinguish Reading context from Generating and add numeric prompt/context/stall detail; MTPLX 2.9.1+ can distinguish Reading context, Reasoning, and Answering and add numeric context/acceptance/stall detail. Details reveals the exact route, first-output timing, and full lane report, while Detailed presentation opens it automatically. The transcript/terminal viewport remains pure black with the same high-contrast ANSI palette in every surrounding theme. Stop agent, Restart agent, bounded case-insensitive Find, and **Copy visible** leave the shared model loaded. A page refresh reconstructs each bounded view from at most 2 MiB of backend memory; the browser stores no transcript. A Terminal handoff remains external: closing that Terminal ends the agent, and the launcher does not pretend it can terminate or monitor it. A secondary Chat is launcher-owned and can be ended independently. Stopping the route closes every owned Hub Console, engine, and relay and invalidates every attachment at once. Single-lane engines queue simultaneous requests; attaching a surface saves model memory, not unlimited parallel throughput.

The next-launch plan is read-only and uses the selected model, engine, context, KV precision, acceleration, and LM Studio request-lane count. It adds checkpoint weights, any MTP/DFlash/ANE companion allocation, architecture-aware full-context KV capacity, a runtime reserve, and a protected macOS reserve. Hybrid models use their declared full-attention layer schedule instead of pretending every linear-attention layer has a growing KV cache. Actual paged-cache residency may be lower, so the result is labelled as a conservative capacity estimate rather than exact process memory.

If current headroom covers the estimate and reserve, Launch proceeds normally. Tight, unavailable, or over-headroom estimates require a separate one-time checkbox. That acknowledgement is hashed to the exact visible launch contract and is ignored after the model, engine, context, KV mode, runtime controls, or other saved setting changes. Planning allocates no port, creates no run directory, and reads no project content.

## Route Check

**Check route** verifies the boundary between the selected engine, exact served-model ID, and work surface before opening it. Opening the dialog builds a side-effect-free plan from the current visible contract and capacity signal. Running it is optional; the clearly labelled action button starts one temporary model load after the plan is ready.

The live pass waits for the exact model at `/v1/models`, sends a bounded synthetic request through Chat Completions or the Codex-facing Responses guard, verifies actual streaming output, records authoritative usage only when supplied, and checks separately exposed reasoning without inferring hidden text. Pi, OpenCode, and Codex also receive one harmless function schema. Rejected tool syntax fails the route; an accepted schema where the model elects to answer in text is an advisory rather than a fabricated tool success.

The check never reads project files, opens a Terminal or Chat, or stores generated response text. It stops a temporary launcher-owned local process, unloads only its uniquely named LM Studio model, or closes only a connected FreeToken bridge before marking cleanup complete; a connected FreeToken server and model are never stopped. A pass proves this bounded protocol contract now; it does not promise every future MCP/tool shape or long-running agent workflow will be supported by that runtime version.

Choose **Verified quick launch** from the optimiser arrow to connect the otherwise separate decisions safely. The launcher first applies a complete, like-for-like measured fastest-engine result; if evidence is incomplete it changes nothing and opens Calibration instead. After **Run Route Check**, a pass or advisory enables **Launch checked route** only once cleanup has finished. That button submits the short-lived receipt, and the backend independently rebuilds the plan and rejects any changed settings, model artifact, runtime build, adapter contract, or receipt older than ten minutes. The receipt exists only in memory, contains no generated response text, and disappears when the launcher restarts.

## Built-in Chat workspace

Primary and attached Chat surfaces use the same workspace. Separate **Queue** and **Stop response** actions let the current local generation continue while later messages wait in order. The composer keeps one compact queued-count and next-message preview; **Manage** reveals edit, reorder, remove, and clear actions only when needed. Recovered or failed queues open that review automatically, remain paused, and require an explicit **Resume queue** click; nothing is transmitted merely because the page or conversation reopened. Waiting text survives a refresh, renderer crash, or conversation switch in the same browser tab. If a queued turn cannot start, it is put back at the front and paused instead of disappearing. A one-lane engine processes resumed messages serially; LM Studio can use the request-lane count selected when its model was loaded.

Focused presentation removes the duplicate Chat heading and replaces the separate route and telemetry cards with one expandable status strip. It keeps the exact model/engine, authoritative TPS, shared request-lane state, and runtime-reported cache truth visible at a glance; route changes and context pressure at 85% or more remain explicit warning badges. Opening **Details** reveals the complete route, token/context meter, lane explanation, cache evidence, and context-trimming action. Saved Chats likewise show one Open or Review resume action per row; Pin, Rename, Export, and Delete sit behind **More**, while cold-resume review keeps engine/model/action visible and folds the secondary route facts behind **Route details**. Detailed presentation opens those diagnostic disclosures automatically without restarting Chat or changing its contract.

On oMLX 0.6.3rc2+, that compact strip can show live Reading context or Generating state plus runtime-reported prefill/decode TPS before the response finishes; Details can add prompt progress, context/generated-token, and prolonged-stall signals. MTPLX 2.9.1+ adds live Reading context, Reasoning, or Answering plus numeric MTP acceptance. Older builds and LM Studio keep the completion path; LM Studio uses exact response TPS/MTP stats when supplied and otherwise uses authoritative usage plus relay timing. The launcher does not invent live TPS when the shared runtime cannot attribute a counter.

While Chat is running, **Controls** opens a right-side drawer instead of returning to the launch form. It shows the locked model/engine/context/output/reasoning contract and lets the system prompt or complete sampling contract be replaced atomically for the next request, including an attached Chat sharing an agent's loaded model. Saving never reloads weights or mutates runtime controls. Invalid values or a stale surface change nothing; queued messages use the controls that are saved when each request actually starts. The system prompt remains active-run state and is not copied into Chat History.

Streaming follows the newest token only while the transcript is already at its live tail. Scrolling upward pauses follow mode, preserves the exact reading offset while the response keeps growing, and reveals **Jump to latest**. Wheel, touch, pointer, and keyboard scroll intent wins even if it lands between a streamed redraw and its scheduled position restore; stale redraw callbacks are ignored. Opening a different conversation or sending a new turn deliberately returns to the live tail. Open thinking panels also remain open across streamed re-renders instead of collapsing under the reader.

The current-transcript bar counts turns and messages and opens **Find in chat** with the button or `Command/Ctrl+F` while Chat is visible. Search covers final answers, user messages, and reasoning text actually emitted by the runtime; previous/next wraps through matching messages, visibly marks matches, and opens a reasoning panel when that is where the match lives. The query is capped at 160 characters, results are bounded to the 512-message History limit, and search state remains only in page memory. Selecting an earlier result also pauses live-tail following, so streamed tokens cannot move the reader away. New turns carry an optional local timestamp into History and Markdown export; older saved turns without one remain undated rather than receiving an invented time.

An accepted prompt and the visible part of its streaming response are also checkpointed about every 1.8 seconds in a separate owner-only `chat-turn-journal.json`. After a refresh or renderer crash in the same browser tab, the newest checkpoint is promoted once into History and visibly labelled **Recovered partial · interrupted**. Both sides of that interrupted turn are excluded from later model requests, so recovery never silently replays a prompt or treats a partial answer as complete. A newer completed History save always wins over a stale checkpoint, and an ordinary completed turn clears its journal entry.

Every completed message keeps the read-only **Copy** action visible, including while a later response is generating. Routine **Edit + retry**, **Regenerate**, **Branch**, and **Continue** actions live behind that message's small More menu so long transcripts stay calm; **Continue answer** remains directly visible when the runtime actually reports an output-limit stop. Edit + retry and Regenerate first save the original conversation, create a child branch, and then generate from the selected user turn. Branch keeps the transcript through the chosen message without generating, while Continue extends an assistant answer using a fixed request-only instruction rather than a fake visible or saved user message. Branch cards record their parent, operation type, and source message so the original path remains clear.

When the runtime explicitly reports that a response reached its configured token/output ceiling, Chat preserves a compact **Response limit reached** cue and changes that message's action to **Continue answer**. The state survives History, branches, interrupted-turn checkpoints, and Markdown export. It is accepted only from authoritative protocol fields such as Chat Completions `finish_reason: "length"` or Responses `incomplete_details.reason: "max_output_tokens"`; the launcher never infers truncation from text length, generic errors, or missing usage, and never starts a continuation automatically. [oMLX 0.6.3rc2 documents the Responses incomplete event and reason explicitly](https://github.com/jundot/omlx/releases/tag/v0.6.3rc2).

When a runtime emits `reasoning_content`, `reasoning`, `thinking`, a typed reasoning content part, or explicit `<think>…</think>` text, the launcher shows it in a visually separate, collapsible **Thinking live / Model thinking** process card. Response text always receives a separate **Answering live** divider while streaming and **Final answer** when complete, including models that emit no reasoning field. If the runtime returns only final content, no reasoning panel is invented. This is model-produced text, not a claim that an unavailable private chain of thought can be recovered.

The response ceiling includes both exposed reasoning and the final answer. If a local Chat Completions server emits exactly that many tokens but incorrectly calls the finish a normal stop, the private relay corrects the terminal event to **length** once authoritative usage confirms the exact boundary. Pi then warns in Hub Console or Terminal that the task can be resumed with `continue`; built-in Chat keeps its existing Continue action. Native Codex Responses traffic receives the matching protocol repair: an exact-ceiling `response.completed` becomes `response.incomplete` with reason `max_output_tokens` in both Hub Console and external Terminal, and the MTPLX Responses bridge applies the same rule. Earlier stream events are not delayed, non-stream JSON is covered, and a normal completion below the ceiling is never changed.

Hub Console also treats Pi's final RPC `message_end` as authoritative. It compares that bounded in-memory message with the deltas already displayed and restores only a missing suffix, or labels and appends the complete recovered block when the streams disagree. If Pi fully settles after exposing reasoning but no answer or tool call, the transcript says **No final answer** and suggests `continue` instead of dropping back to an unexplained idle state.

Assistant answers use a dependency-free, streaming-safe Markdown view for headings, emphasis, lists and tasks, quotes, tables, inline code, and fenced code with a local **Copy code** action. The renderer builds a bounded document structure and then creates the visible elements with text nodes; it never inserts model text as HTML. Raw HTML remains visible text, incomplete streaming code fences remain inert, only `http` and `https` links can open externally, and Markdown image references become labelled links instead of loading remote content. User messages and runtime-emitted thinking remain plain text so quoted input and process output are never mistaken for a formatted final answer.

**Add text** builds a visible, request-only Context Pack from files the user explicitly selects. It accepts up to 24 text/source files, 512 KiB each, 1.5 MiB total, and one million decoded characters. The browser reads the selected text; the backend never accepts or opens a local path. Each file body is surrounded by a locked instruction that identifies it as quoted reference data rather than a system/developer command. Attachments are sent with each new turn, are locked while a response or queued turn is in flight, clear when a saved chat is opened, and are never written to Chat History.

**Add folder** creates Workspace Context without granting the backend general filesystem access. The browser indexes at most 500 supported text/source files and 16 MiB from the one folder explicitly selected. Common dependency, build, cache, generated-lock, minified, binary, oversized, and likely credential-bearing paths are excluded before their text enters the index. For each message, deterministic local retrieval ranks filenames and text against that request, then sends at most 12 excerpts under a conservative budget derived from the selected context, response ceiling, attached text, and current transcript. The UI shows indexed, excluded, secret-risk-blocked, and latest-request selection counts. The index exists only in that browser tab, clears with the chat, and is never written to History.

Completed turns are saved automatically to `chat-history.json`, capped at 100 conversations and 512 messages per conversation. A persistent sidebar keeps recent and pinned conversations beside the live transcript. Each saved row has one compact `⋯` menu for pin, rename, local Markdown export, and second-click confirmed deletion; the full **Chats** manager remains available without loading a model. With Chat already running, **Open** reuses that loaded route. When no route is running, a newer saved chat can instead show **Review resume**: its side-effect-free plan revalidates the exact saved engine, model, project folder, limits, reasoning, sampling, KV precision, and runtime controls, then either reuses an exact resident route or offers a normal consent/capacity-gated model load. The transcript opens only after Chat reaches Running. System-prompt text is never stored, so a chat that originally used one requires re-entry or an explicit continue-without choice before resume. Older chats without the versioned settings snapshot remain readable, searchable, exportable, and deletable but fail closed for cold resume. A route card names the active engine/model/context/output/reasoning contract, warns when it differs from the transcript's latest route, and preserves both started-with and latest route metadata instead of silently rewriting the origin. A manual title survives later auto-saves, branches retain bounded lineage metadata, and optional per-message timestamps record only when a visible turn began. Markdown export is created entirely in the browser without uploading anything.

Unfinished composer text is saved after a short pause to `sessionStorage`, so a refresh or renderer crash in the same browser tab can restore it to the matching active conversation. The draft store keeps at most 20 drafts, 200,000 characters per draft, and 400,000 characters overall; newest drafts win when pruning is needed. A separate queue store keeps only ordered message IDs and text, capped at 32 messages per conversation and one million characters across its retained queues. Newest queues win when browser limits require pruning. It never includes sent messages, system prompts, Context Pack files, Workspace Context indexes/excerpts, model responses, or runtime secrets. Because files and folders are deliberately not stored, review a recovered queue and reattach any needed context before resuming it. **Clear draft** removes the current recovered text, sending or queueing clears it automatically, and closing the tab discards both recovery stores with the browser session.

The active-turn journal is deliberately narrower than Chat History: at most eight recent tab entries, eight million characters in total, and seven days of retention. It contains only the accepted visible prompt, already saved visible transcript, visible partial response/reasoning, small usage fields, and route labels needed to reopen the matching Chat surface. It never stores the system prompt, Context Pack bodies, Workspace Context indexes or excerpts, credentials, runtime secrets, or an assigned API key. Its same-tab identifier lives in `sessionStorage`, so another tab cannot claim the recovery entry merely by opening the launcher.

Each Chat request asks the runtime for streamed token usage. When prompt and response counts are returned, the workspace shows the latest prompt’s exact share of the configured context and stores those small usage counts with the associated assistant message. At 85% or more, a long transcript can explicitly create a new branch containing only the latest eight active messages. No summary is invented and the complete original remains saved. When an engine omits usage, the launcher says it is unavailable instead of estimating runtime usage from characters. Workspace preflight does use a deliberately conservative three-characters-per-token planning allowance only to avoid overfilling the request; it is labelled an estimate and never displayed as engine usage. The history file uses owner-only permissions and excludes system prompts, API keys, project content, Context Pack and Workspace Context bodies, assigned ports, request-only continuation instructions, and any reasoning the runtime did not explicitly return.

## Calibration Assistant

Open **Calibrate** after selecting the model, work surface, context, output limit, reasoning, sampling, and KV precision you actually intend to use. Planning does not start a runtime or write benchmark data. It enumerates engines that can preserve one honest measurement contract, explains every exclusion, and gives the real model-reload and request count before the Run action is available. Cooling is a separate visible measurement control: it defaults to Automatic, is included in the evidence identity, and reaches Maximum fans only when that loud option is explicitly selected in the assistant. When LM Studio's single model-controlled Chat Completions reasoning mode is the only mismatch, the plan normalises every included engine from the selected explicit level to **Model default**. That lets all three engines participate without pretending `auto` and `medium` are identical.

The optimizer arrow is intentionally small: it offers **Use highest-TPS engine**, **Test or review engines**, and **Test route, then launch**. The other ranking goals remain in Calibration's Decision goal selector. A complete matching decision is reused immediately; when evidence is incomplete, no engine or control changes and Calibration opens with the recommended workload selected.

Coding agents default to the four-stage **Agentic** workload; built-in Chat defaults to **Standard**. Quick and Thorough are also available. **Highest generation TPS** is the default decision goal and ranks the median decode speed of each engine's correctness-verified safe route. The same locked run can instead select fastest total workload, fastest first response, lowest unified-memory pressure, or best thermal stability. During a run Calibration shows the latest authoritative generation TPS after each completed sample. Its Result area then shows every compared engine's selected route, decision metric, generation TPS, and bounded accelerator-search size. Calibration does not time one arbitrary accelerated preset: LM Studio checks up to ten MTP depth/minimum/cutoff candidates, oMLX checks up to ten DFlash block/verifier/draft-precision candidates (plus native MTP when available), and MTPLX reloads every verified MTP depth from D1 through the artifact maximum. Only each engine's fastest AR-matching route can enter the cross-engine ranking, and the disclosed reload/request totals are explicit upper bounds because deduplication can finish earlier. Agentic fastest-total ranks the complete staged workload, so its winner can differ from the highest decode TPS when prompt loading or first-output delay dominates. Reopening the assistant preserves its selected cooling mode, and evidence is reused only as one complete shootout rather than splicing routes from separate runs. If a complete compatible matrix already exists, the assistant offers **Use result** plus a separate **Retest engines** action; otherwise **Test engines** starts the normal Engine Shootout with generated prompts, rotating engine order, and cancellable resource gates.

After a trusted result is available, use **Apply measured result** to update the visible engine and safe controls, or **Apply + save profile** to create an auto-measured Launch Profile. Planning and measurement never change the visible reasoning selection. If the comparison was normalised, the Apply button says **+ model default** and explicitly moves the visible setting to the measured contract; an `auto` result is never applied to a later explicit-`medium` request. The profile rechecks the same evidence goal whenever it is used; it does not freeze a stale winner.

## Launch Profiles

Launch Profiles turn a complete visible configuration into a reusable local preset. The saved contract includes engine, model, Pi/OpenCode/Codex/Chat surface, project folder, context and response limits, reasoning, KV precision, runtime controls, and—only for Chat—the system prompt and sampling settings. **Apply** restores that contract without starting anything; **Launch** revalidates it and starts it in one action.

**Keep this engine** preserves the saved runtime and exact controls. **Auto-select from local measurements** reruns the same evidence gate used by the optimiser for highest generation TPS, fastest total workload, fastest first response, lowest memory pressure, or best thermal stability. It switches only when a complete matching matrix has a trusted winner; missing metrics, incomplete engines, changed fingerprints, or a result inside the noise floor keep the saved engine.

Profiles live in `~/Library/Application Support/LLM Launcher/launch-profiles.json`, use owner-only file permissions, and are capped at 32. Missing models and stale runtime routes remain visible as unavailable so they can be edited or deleted, but they cannot be applied. Delete requires a second confirmation and is not recoverable.

Native FreeToken profiles may save the bounded active-sequence, expert-placement, and prefix-cache settings, but never save the synthetic-only experimental approval. Their one-click action therefore becomes **Review**: it applies the settings, opens the amber evidence panel, and waits for a fresh model-bound checkbox before a new load. Applying the profile alone still starts nothing.

## Session Sets

Session Sets save a complete multi-surface workspace that shares one model allocation. Start a normal session, attach the desired Pi, OpenCode, Codex, and built-in Chat surfaces, then open **Sets** and save the current workspace. The primary launch contract holds the engine, model, context/output limits, reasoning, KV precision, and runtime controls; each additional entry contains only its work-surface choice, project folder, agent window, and applicable Chat settings.

**Review opening** is always side-effect free. With no active model it shows one model load, the primary surface, every later attachment, and the current conservative memory decision. With an exact resident model contract it matches only launcher-owned Chat and Hub Console surfaces, then proposes only the missing work surfaces without reloading weights. A different resident engine contract blocks the set rather than stopping or replacing it. The reviewed confirmation is rebuilt under the normal operation lock before anything starts.

Opening is deliberately incremental: the primary model must become ready before later surfaces attach through the ordinary private-relay path. Stop remaining surfaces cancels only work that has not opened; it leaves the loaded model and completed surfaces alone, and a later failure reports the partial result instead of pretending to roll it back. Terminal handoffs are external, so the launcher always plans a saved Terminal surface as a new window and calls out any earlier handoff registration it cannot verify.

Sets live in `~/Library/Application Support/LLM Launcher/session-sets.json`, use owner-only file permissions, are capped at 16, and may contain at most 12 work surfaces. The file stores settings only: no messages, responses, reasoning transcripts, console output, credentials, ports, process IDs, running state, or secrets. **Apply primary** restores only the visible primary settings and starts nothing. Replacement saves the currently running workspace; deletion needs a second click and cannot be recovered.

An experimental native FreeToken approval is also never stored in a Session Set. If reopening would load that model again, the read-only plan is labelled Experimental and its exceptional opening checkbox explicitly includes the current synthetic-only evidence; the backend binds that one approval to the plan before starting. Ordinary Session Sets start from the reviewed action button without another tick. Reusing an already-running exact route does not ask again because it loads no weights or engine.

### Safe Runtime Update Center

The update center deliberately automates only the runtime the launcher can own safely: isolated oMLX command environments. Its locally audited catalog currently contains [oMLX 0.6.4 stable](https://github.com/jundot/omlx/releases/tag/v0.6.4) and retained [0.6.3rc3 preview](https://github.com/jundot/omlx/releases/tag/v0.6.3rc3) rollback, pinned to their full Git commits and GitHub-published CPython 3.11 wheel SHA-256 digests. LM Studio app/runtime packs and the MTPLX app engine remain vendor-owned; their cards link to the official updater rather than imitating an unsafe generic installer.

**Review exact plan** is side-effect free. It binds the release channel, immutable commit, official wheel name and digest, Python interpreter, versioned destination, disk reserve, installed provenance, execution steps, and current rollback path for 30 minutes. A separate checkbox and exact server-generated confirmation are required to start. An install resumes the root-wheel download, verifies its complete SHA-256, then audits the wheel metadata against four disclosed GitHub dependencies fixed to full commits. Those four source packages and binary-only public dependencies are staged into a private wheelhouse, every resulting wheel is hashed, and installation then runs offline from only that inventory. Version, package metadata, dependency, CLI, and native-kernel checks run in staging; generated virtual-environment commands are rebased before atomic promotion, and the complete smoke suite runs again from the final path before an owner-only manifest records trust. A failed or cancelled staging environment—or a newly promoted copy that fails final-path checks—is removed; verified root-wheel bytes remain resumable.

The new copy is never selected automatically and no existing destination is overwritten. The previously selected executable stays live as rollback until **Use for new sessions** explicitly chooses another verified candidate. If an exact catalogued release is already present, the center can match its recorded installation hash to the official wheel, run the same local smoke checks, and add the manifest without downloading or reinstalling it. It starts no server or model during either path; Benchmark Lab remains necessary before calling a runtime or acceleration mode fastest.

### Measured Runtime Promotion

Once two oMLX copies are installed, **Measure update** turns release selection into a controlled same-engine A/B rather than a version-number guess. Planning is read-only: it hashes both exact executable revisions, requires the candidate's official wheel provenance, locks the current visible model and representative workload, counts the generated requests, and shows the execution order and rollback path. The first run measures the selected copy first; matching repeats alternate order to reduce a fixed warm-machine advantage.

Pressing **Measure both copies** loads one copy at a time through a private runtime override that never edits the global selected path. Both use the same checkpoint, AR decoding, full-precision KV, disabled ANE tuning, reasoning, sampling, context, output limit, synthetic warm-up, greedy parity probe, and Quick/Standard/Agentic/Thorough workload. Each route is completely stopped before the other loads. Public unified-memory headroom, thermal state, and Low Power Mode must begin comparably. A candidate is promotable only when output and authoritative token counts match, median and every paired workload stage beat the selected copy by at least 3%, extra peak pressure stays within 512 MiB, and the public thermal state does not worsen.

Only a complete comparison is written to the bounded owner-only `runtime-promotions.json` store; prompts and completions are never stored. **Promote measured candidate** is a distinct second action that revalidates both executable revisions, official provenance, selected rollback copy, Mac identity, and seven-day evidence window before changing the launcher-owned preference. The old copy remains installed for immediate rollback. Direct **Use for new sessions** remains available for expert/manual selection, but it carries no measured-performance claim.

## Current performance findings

- There is no universally fastest runtime. The winning route depends on the exact Mac, checkpoint/quantisation, prompt length, cache hit rate, number of concurrent users, and whether a compatible draft path exists.
- FreeToken's expert-placement and cache ideas are promising for sparse/MoE inference. The separate Apple-Silicon port now proves a local MLX/Metal serving path, but its current Qwen3-MoE, greedy-Chat-only contract is too narrow for a fair fastest-engine matrix. Its live local TPS can guide use now; a connected Linux/NVIDIA route likewise reports useful live TPS but cannot be compared like-for-like with this Mac.
- For one interactive chat or coding agent, one request lane avoids batching overhead. [oMLX documents FCFS scheduling, configurable concurrent requests, and queuing beyond the limit](https://github.com/jundot/omlx/blob/main/README.md); the current launcher contract intentionally gives it one lane. [LM Studio documents parallel requests](https://lmstudio.ai/docs/app/advanced/parallel-requests), and its own mlx-engine benchmarks show that higher parallelism is valuable when several chats are active concurrently. [oMLX 0.6.4 reports 14.6% higher generation TPS and 24.2% lower total time at 32K for one Qwen3.8 Flash-Next workload on an M3 Ultra](https://github.com/jundot/omlx/releases/tag/v0.6.4). [MTPLX 2.10.1 reports 35% faster 98K Flash-Next prefill on an M5 Max and fixes reasoning-only tool turns that returned no visible answer](https://github.com/youssofal/MTPLX/releases/tag/v2.10.1). Those are upstream, hardware-specific findings, so the launcher preserves older baselines as history and requires the same local benchmark before preferring either update for TPS.
- Reusing prompt/KV state is usually decisive for repeated long-context agent turns. [MLX-LM implements reusable cache types](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/models/cache.py), [oMLX documents tiered KV caching](https://github.com/jundot/omlx), [LM Studio reports major repeated/parallel-workload gains from its newer cache architecture](https://lmstudio.ai/blog/mlx-engine-agentic-workloads), and [MTPLX documents its session-cache evolution](https://github.com/youssofal/MTPLX/blob/main/CHANGELOG.md). Availability is not proof that a specific request hit cache, so the launcher waits for runtime token telemetry.
- Maximum GPU offload remains the documented LM Studio default for this all-Apple-Silicon path. [The `lms` CLI documents `--gpu=max` and explicit context loading](https://lmstudio.ai/docs/cli).
- [LM Studio has shipped MTP speculative decoding as a stable feature since 0.4.14](https://lmstudio.ai/changelog/lmstudio), but the launcher still probes the selected local CLI before offering it. LM Studio MTP is enabled only when that CLI advertises enable, disable, maximum draft, minimum draft, and continuation-probability controls and the exact model has a successfully audited MTP sidecar.
- LM Studio's [configuration schema](https://github.com/lmstudio-ai/lmstudio-js/blob/main/packages/lms-kv-config/src/schema.ts) defines the load-time MTP defaults as maximum 3, minimum 0, and probability cutoff 0.00. Minimum may not exceed maximum, and the cutoff is restricted to 0.01 steps from 0.00 to 1.00. Higher minimum/cutoff values generally produce fewer, more selective drafts; they are not assumed faster. Benchmark Lab's bounded tuner starts from the visible combination, explores representative maximums, then refines cutoff and minimum, with at most ten MTP loads plus one AR reference. [LM Studio's speculative-decoding guide](https://lmstudio.ai/docs/app/advanced/speculative-decoding) notes that poor draft acceptance can make speculation slower, which is why only this exact local sweep can replace the conservative settings.
- Speculative decoding is enabled automatically only for a verified matching artifact. [MLX-LM supports draft models and tunable draft depth](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/SERVER.md), while [oMLX 0.6.4](https://github.com/jundot/omlx/releases/tag/v0.6.4) pins the current audited DFlash integration and isolates DFlash from Lightning-MTP model patches; neither fact proves a speedup for an arbitrary local model or agent trace.
- KV quantisation remains manual because it trades memory for numerical fidelity. The optimiser never changes it.

## DFlash 2 status

DFlash 2 now exists upstream and the launcher's oMLX path supports its current settings. The local `Qwen3.8-27B-MTPLX-Optimized-Speed` conversion has the exact 64-layer, 248,320-vocabulary, 5,120-hidden geometry required by [`z-lab/Qwen3.8-27B-DFlash2`](https://huggingface.co/z-lab/Qwen3.8-27B-DFlash2), so it is a structurally valid target. This Mac's last inventory selected the checksum-verified, launcher-managed [oMLX 0.6.3rc3](https://github.com/jundot/omlx/releases/tag/v0.6.3rc3) environment and a pinned local DFlash draft; the verified launcher-managed [0.6.3rc2](https://github.com/jundot/omlx/releases/tag/v0.6.3rc2) environment remains the immediate rollback, and Homebrew 0.5.7 remains separately installed. Stable [oMLX 0.6.4](https://github.com/jundot/omlx/releases/tag/v0.6.4) is now the recommended audited candidate, but it is not selected or called faster until a matching local promotion run wins.

The official oMLX M3 Ultra measurements reported a 1.33–1.43× decode speedup across 4K–32K context for its tested Qwen3.8 DFlash target. The much larger 2.67–3.43× single-user figures on the draft's model card were measured with SGLang on an NVIDIA H200, so they are not predictions for this Mac. The launcher therefore exposes target/runtime/draft readiness separately, uses bounded verifier and precision tuning, and still requires a local A/B result before **Apply fastest safe settings** chooses DFlash 2 automatically. It never silently installs a runtime or downloads weights.

For the selected recommended build, **Run bounded DFlash tune** begins at the visible block/verifier/precision combination, samples useful block-size extremes and interior points, then refines verifier and draft precision. It stops at ten deduplicated DFlash candidates. AR is always measured; native MTP is also measured when the target contains it, so the final recommendation can keep either route instead of promoting the best DFlash candidate in isolation. The selected combination is useful only if its exact target/draft pair, oMLX build, Mac, visible contract, greedy fingerprint, and paired speed floor still match.

The linked repository is the correct draft, but it is not a standalone chat model. Its `DFlash2DraftModel` architecture adds a candidate selector and dynamic convolutions that require DFlash 2-aware serving code. The model card's current SGLang and vLLM examples install unreleased pull-request builds for that reason. On this Mac the selected launcher-managed oMLX 0.6.3rc3 supplies that integration; stable 0.6.4 is the current audited candidate, launcher-managed 0.6.3rc2 remains the immediate rollback, and the older Homebrew 0.5.7 copy cannot serve DFlash 2.

## Neural Engine Prefill Tuner

[oMLX 0.6.3rc2](https://github.com/jundot/omlx/releases/tag/v0.6.3rc2) extends its experimental Qwen prompt-processing path across GPU, Apple Neural Engine, and optional CPU work. Its M3 Ultra release measurements reported roughly 27–28% ANE/GPU prefill gains at 4K and 16K, with larger gains when CPU sharing was enabled. Those are evidence to tune locally, not predictions for a 48 GB M3 Max or a different checkpoint.

The launcher now exposes that tuner without trusting a compiled-but-idle ANE path. It fixes the scheduler shape at 2,048 tokens, runs the upstream GPU baseline and candidates twice, sanitises the returned rows, and then independently requires a positive `[benchmark-ane-profile] operations=N` trace. A recommendation must beat the baseline by at least 3%, survive memory/runtime failure checks, and match the exact model fingerprint, oMLX build, and hardware fingerprint. The accepted settings are written only to that launch's private `model_settings.json`; global `~/.omlx` files are not changed.

This path is intentionally an explicit opt-in. The [upstream implementation](https://github.com/jundot/omlx/blob/main/omlx/patches/qwen35_ane_prefill.py) requantises the ANE slice to INT8, so it is approximate and does not belong in the quality-preserving **Apply fastest safe settings** preset. The launcher's collapsed **Advanced candidate pool** now supports upstream CPU sharing without guessing: it remains off by default, rejects the normal BF16 checkpoint, requires every floating checkpoint tensor plus every MLP gate/up scale pair to be FP16, requires a conservative 16 GiB capacity reserve, and binds the tensor-profile digest to the saved result. Down-projection and GDN CPU candidates are offered only when their own FP16 scale families are present. A CPU recommendation is accepted only inside the upstream fraction bounds and is revalidated immediately before its private settings are written.

For an otherwise eligible BF16 checkpoint, **Prepare copy…** opens a separate read-only plan under that Advanced disclosure. It follows oMLX's tagged [FP16 clone tool](https://github.com/jundot/omlx/blob/v0.6.3rc2/tools/clone_mlx_model_fp16.py) but adds exact source/runtime/helper fingerprints, a 4 GiB disk reserve, symlink and non-regular-file rejection, an unguessable staging folder, cancellation scoped to that folder, and post-conversion tensor name/shape/dtype verification. The source is fingerprinted again after conversion and never edited. Only a completely verified staging copy is atomically renamed to the visible `-fp16` sibling; **Use prepared copy** merely selects it after a canonical rescan and starts no model or tuner.

On this Mac, the 6-bit and 8-bit LM Studio community Qwen models, MTPLX Optimized Quality, and the 8-bit Uncensored model are structurally eligible. `Qwen3.8-27B-MTPLX-Optimized-Speed` is not: its default group size is 32, while the current ANE patch requires 64 or 128. The selected oMLX 0.6.3rc3 passes the guarded minimum runtime and native-kernel prerequisites, while stable 0.6.4 is the current audited candidate. ANE prefill remains off until the tuner records a positive profiler trace and a speedup outside the 3% noise floor for the exact checkpoint.

## Benchmark Lab

Benchmark Lab closes the gap between “supported upstream” and “fastest here.” It measures the currently selected model, runtime, client contract, context/output range, reasoning, sampling, KV precision, and acceleration tuning. Agentic Route Lab measures four related turns: an 8K cold project prefix, reuse of that shared prefix, ingestion of a 4K synthetic tool result, and a warm follow-up. Quick uses 512- and 2K-token prompts, Standard uses 2K and 8K with repeated passes, and Thorough adds 4K, 16K, and 32K coverage.

**Current engine only** compares AR with every structurally verified speculative route in the selected engine. **Compare all engines** is the one-click Engine Shootout: it locks the visible model/client/reasoning/sampling/context/output/KV contract, admits every installed engine that can preserve it, and then measures each engine's fastest correctness-clearing internal route. The first engine rotates after each saved shootout for that model; the first run uses a deterministic shootout-ID rotation. An engine does not need MTP or DFlash to participate; an AR-only engine is still a valid cross-engine competitor.

LM Studio reasoning is protocol-dependent, not absent. Its documented [Chat Completions parameters](https://beta.lmstudio.ai/docs/developer/openai-compat/chat-completions) do not include a selectable reasoning effort, while its [Responses endpoint](https://lmstudio.ai/docs/developer/openai-compat/responses) does. Benchmark measurement uses the common Chat Completions path across engines, so ordinary exact shootouts cannot pretend LM Studio's model-controlled default equals an explicit `medium`. Calibration handles the useful special case without weakening evidence: it compares **all** eligible engines at `auto`/model-default reasoning, stores the result under that exact setting, and says that applying the winner will change the visible reasoning choice. It never reuses that result as evidence for a later explicit-`medium` request.

For a runtime-verified LM Studio MTP model, **Run bounded MTP tune** performs an adaptive coordinate search rather than an unbounded grid. It measures one AR reference, representative draft maximums, continuation cutoffs, and then minimum draft sizes, deduplicating and stopping at ten MTP candidates. Every candidate uses the same suite, authoritative usage, greedy parity probe, fresh model load, and resource-start contract. Only the complete selected combination is stored in current v4 evidence; cancellation, load failure, or a resource mismatch saves nothing. The result can therefore feed **Apply fastest safe settings** with the exact maximum/minimum/cutoff and measured GPU/parallel controls, or keep AR when no candidate clears the 3% median and worst-case floor.

For a recommended-build, exact-pair oMLX DFlash 2 model, **Run bounded DFlash tune** applies the same fail-closed contract to block size, adaptive/fixed/DDTree verification, and native/Q8/Q4/Q2 draft precision. The coordinate sweep starts from the visible settings and stops at ten DFlash candidates. Its final v3 record also contains an AR reference and native MTP when available; cancellation, a changed runtime or pair, load failure, output mismatch, or non-comparable resource start cannot save a partial sweep.

Every route is also sampled for system-wide unified-memory headroom with Apple's unprivileged `memory_pressure -Q` tool and for thermal state with the public `NSProcessInfo.thermalState` API. Before every shootout route, the launcher waits for two stable samples—up to 60 seconds and always cancellable—using a 512 MiB headroom tolerance and the same public thermal/Low Power Mode state. A timeout does not strand the run: measurement continues, but the final comparison rejects mismatched starting conditions. Sampling then continues from that gated sample through model load and measured requests. The record stores cooldown evidence, baseline and minimum headroom, peak pressure delta, starting and worst thermal state, thermal escalation, and Low Power Mode state. This system-wide method works consistently for launcher-owned processes and LM Studio's shared service; because other Mac activity can affect it, a memory-driven engine switch also requires at least a 512 MB advantage.

Each candidate gets a fresh runtime load, a warm-up, a greedy correctness probe, and measured streaming requests. Ordinary suites use cache-isolated prompts; Agentic Route Lab deliberately preserves exact prefixes within each route so it can measure the workload shape described by [MLX-LM's prompt-cache example](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/examples/chat.py) and [LM Studio's agentic-workload measurements](https://lmstudio.ai/blog/mlx-engine-agentic-workloads). The launcher accepts only runtime-reported prompt and completion token counts; it never estimates tokens from characters or network chunks. If a runtime reports `prompt_tokens_details.cached_tokens`, the result shows it; timing alone is never labelled as proof of a cache hit.

An accelerated route must match the AR probe and beat AR by at least 3% in both median and worst paired samples. Otherwise AR wins. The saved result is tied to the exact model/draft file identity, runtime version, hardware fingerprint, and the complete load-time settings of every compared mode. For LM Studio MTP that means maximum draft size, minimum draft size, and continuation-probability cutoff; for MTPLX it means the exact winning depth plus a complete, resource-comparable D1-through-maximum sweep; for DFlash 2 it means block size, verifier, and draft precision. Older v2 LM Studio records lack that identity and are deliberately ignored until rerun. The LM Studio runtime identity also includes the CLI revision, desktop-app version, and a digest of every installed MLX engine pack; an app or MLX-pack update therefore cannot inherit an older MTP/AR winner. Pi, OpenCode, and Codex prefer matching agentic evidence when both workload types exist; built-in Chat prefers ordinary throughput evidence.

Results are stored locally in `~/Library/Application Support/LLM Launcher/benchmarks.json`. They contain settings, timings, token counts, and one-way output hashes—not generated text or project content. Repeating the same route now preserves up to 12 measurements instead of replacing the previous one; the entire store is capped at 192 records. The ordinary model catalog exposes only the newest record per contract, so retained sample history does not bloat every launcher refresh.

**Measurement history** is deliberately stricter than a generic chart. A trend point must still match the model artifact, runtime version, Mac and macOS fingerprint, work surface, suite, context/output limits, reasoning, sampling, KV precision, and generated-input schedule. Bounded tokenizer or terminal-token drift remains usable and is shown as a warning; materially different work is retained as a workload mismatch and never feeds Apply fastest safe settings. Exact evidence older than 30 days receives a rerun advisory rather than being silently discarded.

The bottom-dock **performance receipt** is a bounded projection of that same strict history endpoint, not the looser newest-artifact summary shown by the model scanner. It never starts a model and never turns capability into a speed claim. Fresh trusted engine or route evidence can lead to Apply; stale, tied, partial, missing, and unavailable states stay distinct and lead only to review, explicit measurement, or retry.

Each per-engine trend uses the selected decision goal: generation TPS, total workload performance, first-response latency, memory-pressure delta, or worst public thermal state. Positive percentages mean the latest run improved after accounting for whether lower or higher is better. **Rerun this visible contract** launches a new full Engine Shootout from the controls currently shown; it never reconstructs hidden or stale settings from an old record.

The optimiser drop-up defaults to **Highest generation TPS**, which ranks median decode TPS from each engine's correctness-verified safe route. Calibration and Benchmark Lab also expose four alternatives: **Fastest total workload** ranks aggregate output speed or Agentic staged time; **Fastest first response** ranks median time to first output; **Lowest memory pressure** ranks the measured headroom drop; and **Best thermal stability** ranks the worst public macOS thermal state before using speed as a tiebreaker. Speed/latency leads below 3% and memory differences below 512 MB remain ties. A resource goal is unavailable until every compatible engine has that resource metric. Any measured goal rejects a matrix when recorded starting thermal state, Low Power Mode, or unified-memory headroom is not comparable; the launcher keeps the current engine and asks for a fresh shootout after the Mac settles. The launcher does not offer a “quiet” or “battery” winner because it has no unprivileged, comparable measurement of watts or fan noise.

No goal compares unlike suites or carries a result across a changed model, runtime, Mac, client, context/output range, reasoning, sampling, KV choice, greedy output fingerprint, or actual token/sample contract. Engine Shootout stages records in memory and writes them together only after every engine finishes, so a cancellation or runtime failure cannot promote a partial matrix.
