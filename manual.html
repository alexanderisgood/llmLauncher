01

How it fits together

There are always two layers. The model engine loads the weights and exposes an OpenAI-compatible address. A work surface—Pi, OpenCode, Codex, or the launcher's built-in Chat—sends prompts through the launcher's private route.

The common mistake

Changing coding agent does not load a model. Starting a runtime does not open a coding agent. You need both halves, and they must agree on the model ID, context window, response limit, and API protocol.

02

The easy route: LLM Launcher

  1. Double-click Start LLM Launcher.command.The starter selects an installed Python 3.10 or newer instead of Apple’s older system Python, then opens a page served only on this Mac. Opening it twice verifies and reopens the existing local controller rather than starting a competing copy.
  2. Choose an appearance and information level if you want.The top-bar appearance menu offers neutral Graphite, true-light Daylight, warm Ember, and the original blue/violet Midnight palette. It also offers Focused and Detailed. Focused is the default launch-first view: when a usable saved route exists, a quiet collapsed Saved routes strip can reveal one ready profile, one Session Set, and one resumable Chat without replacing or disabling the normal form or Launch dock. Those actions still use ordinary profile revalidation, Chat route review, or the Session Set review plan. Focused gives Launch configuration the full workspace width, places the three current engines on one desktop row with an automatic two-column narrow fallback, and replaces the mostly empty inspector with one compact live phase/status strip plus Stop and Log controls in the heading. It also uses plain-language performance copy, marks a fresh exact cross-engine winner directly on its runtime card, hides inactive Chat sampling overrides until Custom is selected, and reduces Hub Console route/telemetry to one expandable status strip. Show details or Detailed restores the full inspector, evidence, inventory, helper copy, Route Check, Preview, inactive-control context, and the Console's full route/latency report. Daylight applies to Saved routes, the complete workspace, inventory, progress cards, calibration, benchmark, runtime, setup, ANE, history, and log dialogs—not only the top-level controls. The actual Hub Console terminal viewport deliberately stays pure black with a stable high-contrast ANSI palette in every appearance; only its surrounding controls follow the theme. The browser remembers only the palette and information-level names; neither can change a model, runtime, profile, benchmark, or launch setting.
  3. Optionally add a public model.Open Models, then Find / download a model. Search and inspection change nothing; a pinned download needs a separate review of the model page, license, exact files, destination, and capacity checks.
  4. Choose engine, model, and a work surface.Pick oMLX, LM Studio, or MTPLX, then Pi, OpenCode, Codex, or built-in Chat. The browser restores the last exact visible route only while its runtime, artifact, and surface remain available; otherwise startup chooses an installed compatible route, falling back to built-in Chat when no agent is available. It stores only those three IDs, starts nothing, and never restores or changes limits, reasoning, sampling, KV precision, accelerators, prompts, or folders. A remembered FreeToken route is ignored while that UI feature is off. For an agent, choose the in-launcher Hub Console or the external macOS Terminal fallback. Unavailable combinations are disabled with a reason.
  5. Set context, response limit, reasoning, and optional Chat sampling.The engine and work surface receive the same limits. Custom Chat controls include temperature, top P, top K, presence penalty, frequency penalty, and seed when the route supports them.
  6. Optionally open Sessions.Review the launcher-owned route and a conservative full-context capacity estimate for the next model load. Tight or unknown headroom needs one explicit, exact-contract acknowledgement.
  7. Optionally open Tools → Calibration.The read-only plan identifies compatible engines and the cost of a local comparison. It can reuse a completed matching result or start the displayed plan directly from Test engines.
  8. Optionally open Tools → Launch profiles.Profiles restore the full visible contract. They can keep this engine or safely recheck a locally measured engine goal.
  9. Optionally open Tools → Session sets.Once one model is serving the agents and Chats you want, a set can remember that settings-only workspace and later reopen it through one reviewed model route.
  10. Review the compact performance receipt, then optionally apply a speed plan.The receipt matches strict local history to the visible intelligence, sampling, limits, KV, workload, runtime, model, and Mac contract. Fresh evidence offers Apply; old evidence offers Rerun; ties offer Review; missing evidence opens the matching measurement plan. The main Apply fastest action optimises the current engine. Its arrow menu also offers Best engine + settings, which switches engines only after a complete like-for-like local benchmark matrix proves a winner.
  11. Optionally press Check route.The read-only plan shows the exact temporary load and request count. Run Route Check verifies the real client protocol with synthetic text, opens no work surface, and unloads automatically.
  12. Press Launch or Start chat.The single action uses exactly the values now shown. Agents open in Hub Console by default, or in Terminal when selected, only after the API is healthy; Chat stays in the launcher.
  13. Use Stop owned process when finished.For LM Studio, only the launcher’s model is unloaded and its shared server is left alone. Native FreeToken is launcher-owned and unloads normally. A connected FreeToken route closes only its private Mac-side bridge, leaving the remote server and model running.
The optimiser may changeVerified MTP/speculation, runtime profile, GPU offload, request lanes, and stream batching.
The optimiser never changesModel weights, quantisation, context, max response, reasoning, sampling, prompts, tools, KV precision, or your cooling choice.
“Fastest safe” is evidence-aware, not magic.

For a locally benchmarked artifact the launcher uses that result. Otherwise it applies a conservative runtime or artifact recommendation and labels it honestly. Speculative decoding can win by different amounts at different prompt lengths, so no static preset can truthfully promise to be the absolute fastest for every request.

Refresh is not a backend restart.

The page can read updated HTML and JavaScript while an older Python controller is still resident. The controller detects that source change and refuses any new launch, calibration, route check, download, runtime change, or Session Set open until the launcher is restarted. Stop and cancellation controls remain usable.

Engine switching has a higher evidence bar.

Best engine + settings requires the same model fingerprint, Mac, workload suite, client, context/output limits, reasoning, sampling, KV precision, and sample contract in every compatible installed engine. The measured winner must beat the runner-up by at least 3%. If the matrix is incomplete or tied inside that noise floor, the launcher keeps the current engine and names the missing comparisons.

All generated settings live in ~/Library/Application Support/LLM Launcher. Your existing ~/.pi, ~/.codex, OpenCode, oMLX, LM Studio, MTPLX, and upstream FreeToken configs remain untouched. The launcher does keep its own owner-only FreeToken connection record. Every launcher-created work surface uses a distinct key for a private localhost relay; native routes stream directly, MTPLX Codex traffic is translated inside that relay, and a connected FreeToken route keeps the upstream key and direct address out of each agent.

02A

Model Library: understand an artifact before launching it

Open Models in the top bar for one searchable view of every detected local target checkpoint across oMLX, LM Studio, and MTPLX. FreeToken-only remote models and compatibility rows remain in backend data but are omitted from visible cards, filters, actions, and counts while its UI flag is off. The report comes from the same scanner and compatibility policy that gate Launch, so it does not maintain a looser second list.

  1. Search or filter the catalog.Filter by engine, ready work surface, or doctor state. An engine filter deliberately keeps incompatible checkpoints visible, scopes each badge, route count, diagnosis, and detail card to that engine, and hides the unrelated engine cards. Search also covers architecture, format, quantisation, origin, path, decode modes, and compatibility explanations.
  2. Separate compatibility from installation.An artifact can be structurally compatible with an engine while its runtime is missing. A route is marked ready only when the artifact, installed engine, work-surface command, protocol matrix, and enforceable reasoning controls all agree.
  3. Read the doctor, not just a green badge.The checks cover complete weights, loadable installed engines, usable engine/surface pairs, accelerators, and matching saved benchmark runs. AR-only is a valid advisory; an unmeasured accelerator is available but not claimed faster.
  4. Select without starting.Use with oMLX, LM Studio, or MTPLX puts that route into the normal launcher. It preserves the current Pi/OpenCode/Codex/Chat choice so any incompatibility remains visible, and it starts no process.
Opening or refreshing may doRead known local model metadata, installed command status, and launcher-owned benchmark evidence.
It never doesLoad an engine, download or delete weights, contact the internet, alter a checkpoint, launch an agent/chat, or reopen a hidden engine.
02B

Model Acquisition: add one pinned model safely

Choose Find / download a model at the bottom of Model Library. Opening the center checks only local downloader status. Public Hub search and repository inspection happen only when you press their buttons; they run anonymously with implicit Hugging Face account tokens disabled.

  1. Search or enter a repository.Search sends only the visible search phrase. Direct inspection sends one public owner/model ID and optional branch, tag, or commit. Gated/private repositories are not accessed with saved credentials.
  2. Pin before planning.Inspection resolves the requested revision to an immutable commit and reads its exact public file tree. It creates no model directory, downloads no weight, and starts no runtime.
  3. Choose one complete artifact.A standard MLX checkpoint needs root metadata and complete safetensors weights. For GGUF, choose one quantisation or complete shard group; the launcher never downloads every quantisation. Draft-only components and custom-code repositories are blocked as standalone chat models.
  4. Review the whole contract.The plan names the license, full commit, exact files and available SHA-256 checksums, fixed destination, existing/resumable bytes, free-space reserve, conservative memory fit, and expected engines. Expected compatibility is not benchmark evidence.
  5. Give one explicit approval.The checkbox confirms the model page, license, exact commit, selected file set, and destination. Approval is bound to that plan and expires after 30 minutes.
  6. Stop safely or verify completely.Stop preserves completed files and Hub resume metadata. Completion requires exact sizes, every published LFS checksum, and MLX safetensors completeness/structure or valid GGUF headers before the launcher marks the acquisition verified.
  7. Return through Model Library.Open Model Library performs the ordinary local compatibility scan. Only those results determine available engines and work surfaces; Benchmark Lab still determines which compatible route is fastest on this Mac.
Approved acquisition may doCreate or resume one launcher-marked repository folder beneath LM Studio, oMLX, MTPLX, or Documents/models and keep a private progress log.
It never doesUse a saved Hub token, overwrite an unowned folder, execute downloaded code, start a model, alter agent settings, choose every GGUF, delete partial files, or claim a fastest engine.
DFlash 2 remains a paired setup path.

z-lab/Qwen3.8-27B-DFlash2 is a draft component rather than a standalone Chat checkpoint, so general acquisition intentionally blocks it. Use Setup Assistant with a geometry-matched target and a DFlash-aware oMLX runtime.

Why the local-directory path is resumable.

Hugging Face documents that hf download --revision … --local-dir … preserves repository structure and local metadata so unchanged files are not fetched again. The launcher additionally supplies only the selected filenames and verifies the result. See the official CLI guide and download guide.

02C

Runtime Manager: know exactly what will launch

Open Tools → Runtimes to inspect the executable behind each engine. The check stays local: it reads known paths, app versions, local LM Studio runtime-pack folders, and command versions without starting an app or contacting an update server. Focused presentation shows the three compact engine summaries first; open an engine's Details only when you need paths and evidence, or open Advanced runtime tools for isolated oMLX installation and A/B measurement. Detailed presentation expands both layers automatically.

  1. Review the selected copy.Each card shows the exact executable path and version used by new sessions. Duplicate installs are separate so an older shell command cannot masquerade as the app-managed engine.
  2. Compare it with an audited release snapshot.The 23 August 2026 catalog records official oMLX 0.6.3rc2, LM Studio 0.4.21+2, and MTPLX 2.9.1 release pages, key claims, and a safe evaluation order. The comparison is static and local; an unknown or newer local version is labelled for review rather than silently called current.
  3. Read the capability checks.oMLX separates core serving, the DFlash 2 build, and the native Qwen kernel. LM Studio separates the desktop app, CLI, local MLX packs, load-time MTP flags, and benchmark identity. MTPLX reports its app-managed engine and shadowed copies.
  4. Review a pinned oMLX update plan.The Safe Runtime Update Center contains audited stable and preview wheels with full commits and official SHA-256 digests. Planning checks the versioned destination, Python 3.11, free-space reserve, installed provenance, exact steps, and rollback without using the network or creating a folder.
  5. Approve installation separately.An approved install verifies the exact root wheel, checks its four GitHub source dependencies against audited full commits, and stages those builds plus binary-only public dependencies in a private wheelhouse. It hashes that inventory, installs it offline, smoke-tests the isolated environment, records the evidence, and promotes it atomically. An already-installed matching copy can be verified locally without a download.
  6. Measure an installed update before switching.Choose a representative workload, then press Measure update on a checksum-verified oMLX copy. Planning hashes both executables and locks the current visible model without starting anything. Measured Runtime Promotion begins when you press Measure both copies, then runs one cache-isolated AR route at a time with generated prompts, matching settings, deterministic output checks, and comparable public memory and thermal conditions.
  7. Promote only complete evidence.The candidate must match output and token counts, beat the selected copy by at least 3% at the median and in every paired stage, add no more than 512 MiB peak pressure, and reach no worse thermal state. A passing result still needs a separate Promote click within seven days; both executable revisions and the rollback selection are checked again.
  8. Switch only if you mean to.Use for new sessions selects an already-installed, version-reporting candidate. It writes one launcher-owned preference and then rescans model capabilities. It does not modify PATH, update a package, or remove the other copy.
  9. Keep vendor-owned updates with their vendor.LM Studio app/runtime packs and the MTPLX app engine keep their official update handoffs. oMLX’s signed app is still preferred for a full desktop installation; the launcher-managed path owns only isolated command environments.
Opening it may doRun bounded local version checks and inspect app/runtime metadata.
Opening it never doesStart LM Studio, load a model, use the network, install or remove software, or change the selected path.
Installation and measurement still never switch the runtime.

The selected executable remains unchanged after install, verification, or a completed A/B. Promote measured candidate is a separate revalidated switch; Use for new sessions remains the manual path. Every other installed copy stays available as rollback, and measured evidence—not release recency—supports a performance claim.

FreeToken has two retained but UI-hidden routes.

The official released server still targets Linux/NVIDIA. The launcher can also detect the separate experimental Apple-Silicon MLX/Metal port without pretending it is the upstream CUDA build. Native format and memory compatibility are checked per checkpoint by a versioned local preflight, while the separate qualification object decides whether that checkpoint is amber experimental or exactly real-weight qualified. Version 1.66 hides both routes from the interface without deleting the implementation or saved data.

02D

Sessions & capacity: know what is loaded before launching again

Open Sessions in the top bar to inspect the current launcher-owned route and the next launch's conservative unified-memory budget. Opening the dashboard is read-only: it does not start a runtime, allocate a port, create a run directory, read project content, or stop anything.

  1. Check public Mac capacity.The dashboard reads Apple's unprivileged system-wide memory_pressure -Q headroom plus public thermal and Low Power Mode state. These signals include every app on the Mac; they are not presented as exact process RSS or GPU allocation.
  2. See the ownership boundary.The active card lists the route plus the exact engine, loader, private relay, and Hub Console processes owned by this launcher. A selected macOS Terminal remains an external handoff and external runtimes are never adopted. For LM Studio, only the uniquely named loaded-model slot is owned; the shared service remains running. Native FreeToken is a launcher-owned process; for connected FreeToken only the local bridge is owned and the remote server/model remain outside Stop.
  3. See the real request queue and TPS.Live request scheduler labels active and waiting generations by surface and protocol, shows FCFS position plus wait/run/first-output timing, and can cancel one request without stopping the whole model. oMLX 0.6.3rc2+ can supply live Reading context/Generating state, prefill or decode TPS, prompt progress, context/generated-token counts, and numeric stall age through its protected activity endpoint. MTPLX 2.9.1+ can additionally distinguish Reasoning from Answering and report MTP acceptance. The launcher attaches either only when exactly one relay request and one exact-model engine record can be matched; ambiguity fails closed. Completed rows use exact LM Studio response TPS/MTP stats when supplied; otherwise they show conventional decode and end-to-end TPS only from runtime token usage plus relay timing. Text is never converted into a guessed count. LM Studio stays completion-only because its shared service has no safely attributable live request counter here. It keeps at most 32 numeric metadata rows and never retains prompt, answer, reasoning, tool, model-ID, file, project, or credential content.
  4. Separate residency from cache proof.Cache Observatory names the configured engine policy, then counts only runtime-reported cache tokens from built-in Chat. “Engine resident” means the weights are loaded; “Prefix reuse confirmed” requires an observed turn with cached prompt tokens. Timing alone never becomes a claimed hit.
  5. Reuse the loaded model.After a normal route reaches Running, choose another compatible Pi, OpenCode, Codex, or Chat surface. The preview keeps the model ID, engine, context, response ceiling, reasoning, KV mode, and acceleration fixed and explicitly promises no engine start or weight load.
  6. Use the main warm action.When every visible engine control exactly matches the resident route, the ordinary Launch button becomes Open warm chat/Open Pi/OpenCode/Codex. It adds the selected surface with zero weight reloads. A backend confirmation binds the active run, checkpoint fingerprint, limits, reasoning, and engine options; any drift disables the action.
  7. Understand attachment ownership.Hub Console is launcher-owned: each attached agent gets a keyboard-accessible tab with generating, queue, stopped, failed, and unread-output state. Switch agents without reloading the model, use bounded Find or Copy visible, and Stop or Restart only the selected agent. Direct keys and paste stay bound to their original tab and the console resizes with the page. In Focused view, one status strip keeps the exact agent/model, authoritative TPS, lane, and failures visible. oMLX 0.6.3rc2+ can distinguish Reading context from Generating; MTPLX 2.9.1+ can further distinguish Reasoning and Answering. Details reveals the exact route, first-output time, numeric prompt/context/acceptance/stall signals when available, and complete lane report, while Detailed opens it automatically. Its terminal viewport is always pure black with one stable high-contrast ANSI palette, even when the surrounding app uses Daylight. The bounded parser preserves the agent TUI’s own safe ANSI colour and emphasis, so its thinking, status, tool, and answer cues need not look identical; the launcher does not guess those semantics when the agent emits plain text. A refresh rebuilds each screen from its at-most-2-MiB backend memory buffer; browser recovery stores only surface IDs, visibility, and numeric seen offsets—never terminal text. The macOS Terminal choice is an external handoff; close that Terminal to end the agent. Secondary Chat is launcher-owned and can end independently. Every surface receives its own relay key; Codex uses bounded native Responses on oMLX/LM Studio and the private Responses-to-Chat bridge on MTPLX.
  8. Choose idle unloading deliberately.Off keeps the route open until Stop. For oMLX, MTPLX, or native FreeToken, 5–120 minutes counts only while no relayed work is active or queued and then unloads the owned process. For connected FreeToken it closes only the private bridge and leaves the remote server/model alone. LM Studio disables this option because independent clients may use its shared loopback server outside the relay.
  9. Review full-context capacity.The estimate combines checkpoint weights, MTP/DFlash/ANE companion allocations when selected, architecture-aware KV capacity at the full visible context, LM Studio request lanes, a runtime reserve, and a protected macOS reserve.
  10. Approve only a tight or uncertain plan.Enough headroom needs no extra action. A plan that consumes the protected reserve, exceeds current headroom, or lacks attention geometry/headroom telemetry enables a one-time checkbox.
  11. Launch the unchanged contract.The approval is bound to a hash of the exact visible settings. Launch resamples capacity and ignores the approval after any model, engine, context, KV, sampling, reasoning, project, or runtime-control change.
What the estimate accounts forWeight files, verified companion artifacts, full-attention KV geometry and precision, parallel lanes, runtime working space, current system-wide headroom, and protected macOS capacity.
What it does not claimExact residency, process RSS, GPU-only bytes, future prompt length, swap behavior, or permission to stop an unowned process.
Hybrid attention is not treated like a conventional transformer.

When a checkpoint declares its per-layer schedule, only growing full-attention layers enter the KV formula; linear-attention layers are not falsely multiplied by the entire context. If the required geometry is absent, the launcher says so and requires review instead of inventing a precise number.

One model allocation, several surfaces.

The launcher blocks a second owned model load but allows up to 12 compatible surfaces to reuse the one active allocation through one private relay. This saves weight and base runtime memory; it does not manufacture throughput. Current oMLX and MTPLX contracts expose one scheduled lane, while LM Studio uses the exact parallel count selected when the model was loaded. Excess work waits FCFS in a bounded queue.

Activity, console output, and cache evidence are different private records.

The relay retains at most 32 content-free completed request rows in memory for all launcher-created surfaces. Its speed parser reads only bounded response framing and authoritative usage integers: decode TPS is output after the first token divided by decode time, while end-to-end TPS includes first-output latency. For an unambiguous active oMLX 0.6.3rc2+ or MTPLX 2.9.1+ request, a transient numeric engine summary can augment that row. The oMLX admin cookie remains only in controller memory and is destroyed with the route. Engine request/session/model IDs, unrelated loaded-model records, recorder paths/history, and generated-text tails are discarded and never published or persisted. Cache Observatory separately retains at most 64 number-only built-in Chat observations. Hub Console may display whatever its agent prints, including project content, but caps that byte stream at 2 MiB in process memory and never writes a transcript. All records clear when the route stops. No TPS is estimated, and agent response bodies are never promoted into cache claims.

02E

Route Check: prove the connection before opening an agent

Press Check route after choosing the exact runtime, model, work surface, context, response ceiling, reasoning, sampling, KV mode, and acceleration controls you intend to launch. Opening the dialog is side-effect free: it validates the same contract and current capacity without allocating a port, creating run files, or loading weights.

  1. Review the route and capacity.The plan names the engine, model, work surface, actual wire protocol, model-load count, generated-request count, and any memory advisory.
  2. Run one temporary load.The live button remains disabled until the exact plan is ready. Pressing it starts that displayed plan directly; one route runs at a time and Stop remains available throughout model loading and generation.
  3. Prove the exact model ID.The runtime must list the private served-model identifier at /v1/models; a merely open port is not enough.
  4. Exercise the client-facing protocol.Pi, OpenCode, and Chat receive a bounded Chat Completions stream. Codex is tested through the same temporary Responses guard used by normal sessions; for MTPLX, that check also proves the real Responses-to-Chat translation and function-tool route.
  5. Check agent tools separately.Agent surfaces receive one harmless synthetic function schema. Rejected syntax fails the route. If the schema is accepted but the model chooses ordinary text, the result is an advisory rather than a claimed tool call.
  6. Read evidence, not guesses.Streaming, authoritative token usage, and separately exposed reasoning each have their own result. Missing usage is never estimated from characters, and hidden reasoning is never invented.
  7. Let cleanup finish.No Pi, OpenCode, Codex, or Chat window opens. Generated response text is not stored. Temporary local processes are stopped, only the check’s uniquely named LM Studio model is unloaded, or only a connected FreeToken bridge is closed. A connected FreeToken server/model is never stopped.
What a pass provesThe selected model, authentication, response ceiling, stream transport, client protocol, and applicable tool schema worked through a bounded synthetic request now.
What it cannot promiseEvery future MCP namespace, every tool shape, semantic tool choice on every prompt, long-session stability, or performance under another Mac state.
Advisory is intentionally different from failure.

A valid JSON fallback, omitted usage telemetry, no separately exposed reasoning on a tiny prompt, or a model electing not to call an accepted tool can still leave the core route usable. A missing model, rejected protocol, empty response, or rejected agent tool schema is a failure.

Verified Quick Launch connects measurement to a checked launch.

Open the arrow beside Apply fastest safe settings and choose Verified quick launch. A complete local matrix selects the measured fastest compatible engine; missing evidence opens Calibration without changing the route. After you press Run Route Check, Launch checked route appears only when the exact route passes or advises and its temporary model has fully unloaded. Its memory-only receipt lasts ten minutes and is bound to the visible settings, model fingerprint, runtime build, and launcher adapter contract. Any change, expiry, failed cleanup, or launcher restart requires a new check. The backend validates the proof again before creating launch files or starting a surface.

02F

Calibration Assistant: choose the best engine for this model

Open Calibrate after choosing the model, work surface, context, output limit, reasoning, sampling, and KV precision you intend to use. The first screen is a side-effect-free plan: it does not start a runtime, load a model, or write a result.

In the default Focused information level, the assistant shows the three choices, one Result area, progress, and the relevant action. The locked route matrix and per-engine diagnostics move behind Full details. That button changes presentation only; it cannot alter the plan. Detailed information level shows the full plan immediately.

The small arrow beside Apply fastest safe settings contains three choices: use the fastest measured engine, test or review engines, or test the chosen route before launch. A complete measured winner or noise-floor tie is reused immediately. If comparable evidence is missing, every visible engine and control stays unchanged while Calibration opens with the recommended workload selected.

  1. Review the locked contract.The assistant validates the same visible settings as Launch, then includes installed engines that share the exact model-artifact fingerprint and can preserve the measurement contract. If an explicit reasoning level would exclude an otherwise compatible single-mode engine, every included engine is visibly normalised to model-default reasoning for this calibration. Every remaining exclusion carries a specific reason.
  2. Choose the workload, goal, and cooling.Agentic is the default for Pi, OpenCode, and Codex; Standard is the default for Chat. Quick and Thorough cover shorter or longer prompt ranges. Rank the one matrix by total workload speed, first response, memory pressure, or thermal stability. Cooling starts on Automatic. Maximum fans is used only when you explicitly choose the loud option in this assistant.
  3. Know the cost before running it.The plan shows the eligible engines, model reloads, and generated request count. It also checks for an existing complete result that still matches every fingerprint and control.
  4. Use an existing result or run the test.A completed matching matrix can be used immediately. Otherwise the clearly labelled Test engines button starts the exact visible plan without a second checkbox.
  5. Apply the measured result.Completion returns to the same plan with the trusted winner or a noise-floor decision. Measurement alone leaves the visible launch settings unchanged. If reasoning was normalised, Apply explicitly changes the visible reasoning choice to model default so the evidence remains exact; Apply + save profile records that measured contract in an auto-measured Quick Launch preset.
Planning may doValidate visible settings, inspect local runtime/model metadata, count the real shootout schedule, and read matching benchmark evidence.
Planning never doesStart an engine, load weights, send prompts, write benchmark data, change visible settings, or save a profile.
Measurement uses the proven Engine Shootout path.

Prompts are generated by the launcher rather than read from the project folder. Each route receives a fresh model load, correctness probe, authoritative token-count check, and bounded cancellable resource-stabilisation gate. Only one route runs at a time. Stop is safe and discards the staged matrix instead of promoting partial evidence.

Normal cooling does not mean silent inference.

The launcher never promotes MTPLX to maximum fans through Apply fastest or Calibration. Automatic and System controlled modes can still let macOS increase cooling during a sustained local-AI workload. Choose Quick when you want a smaller measurement at work, and use Maximum fans only as an explicit loud-mode benchmark choice.

LM Studio does have model reasoning.

Its common Chat Completions route lets the model/template control reasoning but does not expose the low/medium/high selector available on LM Studio's Responses route. The assistant therefore calls it model default, not “no reasoning.” To include LM Studio without comparing unlike settings, Calibration moves every engine in that measurement to model default and stores the winner only under that exact reasoning contract.

“Best” stays tied to the real job.

The selected model artifact, Mac, runtime builds, work surface, context/output limits, reasoning, sampling, KV precision, workload, and generated-input schedule must match. Exact greedy parity is still required between AR and acceleration modes inside each engine. Across different engines, a changed output fingerprint is shown as a warning rather than discarding the run when prompt and response token counts remain inside tight bounds. A missing engine, incompatible control, failed route, material workload mismatch, environmental mismatch, or result inside the 3% speed noise floor keeps the current engine.

02G

Launch Profiles: save a complete local route

Open Tools → Launch profiles to turn the current visible configuration into a reusable preset. The newest usable visible profile can appear inside the collapsed Saved routes strip, where Launch calls the same revalidation path rather than bypassing the profile manager. A profile records the engine, model, work surface, project folder, context and response limits, reasoning, KV precision, and the controls belonging to that runtime. A Chat profile also records its system prompt and model-default or custom sampling controls.

  1. Name the current setup.The launcher validates the model, installed engine and client, folder, token limits, reasoning level, KV choice, and every runtime option before writing anything.
  2. Choose the engine behaviour.Keep this engine restores the exact saved runtime. Auto-select from local measurements rechecks fastest total workload, first-response latency, memory pressure, or thermal stability each time the profile is applied.
  3. Use Apply or Launch.Apply only updates the visible controls. Launch first revalidates and applies the profile, reruns its measured decision if requested, then submits the same visible contract through normal launch validation.
  4. Re-approve experimental FreeToken per model run.A native FreeToken profile can remember active sequences, expert placement, and prefix-cache settings, but never the synthetic-only approval. Its Launch action becomes Review, applies the settings, opens the amber evidence panel, and waits for a fresh model-bound checkbox.
  5. Update or delete deliberately.Edit makes the next save replace that preset with the current visible settings. Delete requires a second click and cannot be recovered.

FreeToken → native Chat or connected agents

Temporarily hidden from the launcher UI.

Version 1.66 keeps the integration, connection record, bridge, native-port validation, and tests, but excludes FreeToken from runtime choices, tool inventory, Model Library, calibration, Saved routes, profile/Session Set actions, and cold resume. Existing transcripts and saved route data are preserved. Re-enable the one UI_FEATURES.freetoken flag only when this route is ready for normal use.

FreeToken has two distinct launcher routes. The experimental Apple-Silicon MLX/Metal port runs compatible local checkpoints under launcher ownership. The official CUDA service remains a separately operated connected engine whose served models can be offered to Pi, OpenCode, Codex, or Chat through a private Mac-side bridge.

  1. Separate compatibility from qualification.The launcher detects the separate port in the sibling Code/freetokenport environment or standard command locations. Scanning calls only ft macos-inspect --json; it loads no weights and accepts only schema v1/API 1.0, local-files-only security, Qwen3-MoE, complete local files, a supported working set, and a valid runtime-owned qualification receipt. Review local models opens the read-only library already scoped to FreeToken, where every detected checkpoint stays visible with its exact rejection reason.
  2. Read the amber experimental state literally.The current port has end-to-end evidence for a tiny synthetic checkpoint path, not for a real large checkpoint. A compatible existing local model is labelled Experimental rather than Ready and requires one model-bound experimental-run checkbox before Preview or Launch. The backend enforces the same approval. The launcher does not offer or recommend a large model download for this state.
  3. Use the native milestone within its real limits.Native FreeToken currently supports built-in streaming Chat, greedy decoding, continuous batching, exact-prefix caching, and expert placement. It does not yet support custom sampling, tools, Pi/OpenCode, or the Responses API/Codex. More than one active sequence cannot be combined with prefix-cache entries.
  4. Launch native safely.A second exact preflight precedes every start. The launcher binds ft macos-serve to 127.0.0.1, disables downloads and remote code, verifies the exact binary/checkpoint/qualification/live-health contract, never enables the unsafe working-set override, and owns Stop and idle unload. A future qualified-real-checkpoint badge is allowed only when the port ties immutable checkpoint identity and fingerprint to successful real-weight serving and token generation.

The bridge keeps one clear security boundary.

The launcher stores the upstream key only in an owner-readable connection file, never sends it back to the page, allows only the bounded Models, Chat Completions, and Responses routes, verifies HTTPS, follows no redirects, enforces the chosen served-model ID, and gives each work surface a separate local secret.

06

What the controls mean

Context

The full token budget for instructions, conversation, source reads, tool results, reasoning history, and the next response. Bigger uses more memory and makes each long turn slower.

Max response

The most tokens one model turn can generate. Set it high enough for reasoning plus a tool call. This is not the total task budget.

MTP

Native multi-token prediction. Matching draft heads propose tokens; the target verifies them. It is a speed path, not permission to attach unrelated weights.

DFlash 2

A different speculative path requiring a matching draft, runtime support, and pairing verification. It is not a universal “make faster” switch.

ANE prefill

An experimental prompt-processing split across GPU and Apple Neural Engine. It needs a per-Mac tune and positive hardware-operation proof; the current INT8 ANE slice is approximate.

KV cache

The model’s memory of previous attention states. Quantising it saves RAM but can alter numerics, so it remains a manual amber control.

Reasoning

How much hidden thought the model is allowed or encouraged to use. The optimiser preserves it; lowering it can reduce both latency and answer quality. “Model default” is used when a runtime cannot prove support for graded effort—for example the current Ornith template through Codex + oMLX.

What about MLX.fast?

MLX.fast is a serious optimisation competition, not a library of portable launcher settings. Its results are correctness-gated on exact model bytes, custom Swift/MLX/Metal code, fixed prompts, and specified Apple hardware. They are useful engineering evidence, but an MTP depth or kernel win from its Qwen track cannot be copied safely into oMLX, LM Studio, or MTPLX. LLM Launcher therefore treats it as a research reference only; Apply fastest safe settings can promote a measured winner only through Benchmark Lab’s local, fingerprint-bound evidence.

What currently matters most for speed

For one interactive session, keep one request lane. For several simultaneous chats, batching/parallel lanes can improve total throughput. In repeated long-context agent work, prompt/KV-cache hits can matter more than peak decode tokens per second. Maximum GPU offload is the documented LM Studio path on this Mac. Speculative decoding is worth enabling only when the exact draft/MTP pairing is verified and wins the matching prompt/cache workload; KV quantisation remains a separate manual memory-versus-fidelity choice.

08

Prevent the truncation loop

The red “response was truncated” messages you saw can come from two different ceilings:

  1. Response ceilingThe model reached max_tokens before emitting a tool call or final stop.
  2. Total context ceilingPrompt history + requested response no longer fit the runtime’s real context window.
history + tool results + reasoning + next response≤server context window

LLM Launcher gives the runtime and work surface the same real context. It does not advertise 131K to Pi, OpenCode, Codex, or Chat while secretly serving 32K. Pi/OpenCode and built-in Chat receive the exact output limit. Codex receives the exact context and an aligned compaction threshold, while a private streaming guard adds the selected max_output_tokens to every Responses request. If the chosen model/context will not fit memory, the correct behaviour is to stop with an error—not silently shrink context.

Built-in Chat now distinguishes an authoritative response-ceiling stop from an ordinary completed answer. Chat Completions may report finish_reason: length; Responses may report response.incomplete with incomplete_details.reason: max_output_tokens. Only those explicit protocol reasons produce the saved Response limit reached cue and Continue answer action. A generic incomplete/error status, apparent sentence cutoff, or token count alone does not.

For a 131,072-token Qwen coding session, keeping a 16,384-token maximum response leaves room for the current turn while Pi manages history. A single request can still legitimately need more than 8K when it reasons and emits a large write, so the output ceiling must not be mistaken for a task-level token target.

Troubleshooting

My model is shown as “Downloading”

One or more .part files or indexed shards are missing. Let the original launcher finish, then press Rescan folders. Ornith was detected this way while downloading and is now correctly shown as ready.

MTP is disabled even though the model name says MTP

The selected runtime has not verified compatible MTP tensors. A sidecar that MTPLX understands is not automatically loadable by oMLX. Choose MTPLX for an MTPLX-optimised artifact or use AR.

Port 8000 is already in use

oMLX and MTPLX both default to it. The unified launcher allocates a free loopback port and creates the matching temporary agent provider. With direct commands, choose another port in both the server and provider configuration.

Where did FreeToken go?

Version 1.66 temporarily hides its UI while keeping the implementation and saved data intact. It cannot be selected, benchmarked, restored from a saved shortcut, or cold-resumed until UI_FEATURES.freetoken is deliberately re-enabled.

Can FreeToken run directly on this Mac?

The official CUDA release still cannot. The separate experimental MLX/Metal port can run natively when its versioned preflight accepts a complete Qwen3-MoE checkpoint and working set. Its current qualification is tiny-synthetic only, so the launcher labels an existing compatible checkpoint Experimental and requires explicit approval instead of calling it Ready or suggesting a large download. In this milestone the route is built-in greedy Chat only; use a connected server for the broader upstream feature set.

Launch says to review Sessions & capacity

The latest macOS headroom sample could not preserve the conservative full-context estimate plus its protected reserve, or the checkpoint lacks enough attention geometry to prove that estimate. Open Sessions, review the weights/KV/runtime figures, and select the one-time checkbox only if you accept possible compression or swap. Changing any visible launch setting invalidates that approval.

Pi, OpenCode, or Codex opens but cannot see the model

Check that the server’s /v1/models list contains the same ID used by the agent. Codex needs native /v1/responses on oMLX/LM Studio or MTPLX’s Chat Completions route through the launcher bridge. The unified launcher checks the selected path before opening the agent.

The answer truncates again

Open Run status → View log. Confirm whether the request ended at the response limit or overflowed total context. Increase only the relevant limit and keep the server and agent values aligned.

Chat starts but a turn fails

Open View log and check the error shown in the conversation. The built-in chat requires the active run to remain healthy and accepts only text user/assistant history. A stale page cannot send to a newer run because every turn is bound to its launch ID.

Benchmark Lab will not run

Current engine only needs at least one structurally verified accelerator in addition to AR. Compare all engines instead needs at least two installed engines that preserve the exact selected model, work surface, reasoning, sampling, context/output limits, and KV precision. No normal run may be active. The dialog shows why each engine is included or excluded.

Model Acquisition will not enable Download

Choose one supported exact MLX or GGUF file set, then resolve the first blocked check. Common causes are a gated/private or draft-only repository, custom root code, a Hub file marked unsafe, an existing destination not owned by the same pinned plan, insufficient free space, or a missing downloader. When every check passes, review the linked model page/license and select the separate consent checkbox. An active launch, check, benchmark, Setup download, or ANE measurement must finish first.

Setup Assistant will not enable Download

The selected oMLX model must have the exact published DFlash 2 target geometry, the Hugging Face downloader must be available, there must be enough free space for the remaining bytes plus the reserve, and no launch or benchmark may be active. After those checks pass, review and select the separate consent checkbox.

ANE Tuner is read-only or rejected its result

Read-only means at least one checkpoint, selected runtime version, native-kernel, or memory check failed; the dialog names it. ANE tuning needs oMLX 0.6.3rc2 or newer and the selected installation must pass oMLX’s native Qwen kernel self-check. CPU-sharing candidates additionally require an all-FP16 clone, matching gate/up scale pairs, a 16 GiB reserve, and an unchanged tensor-profile digest. A completed run is still rejected when it lacks positive profiler operations, records a runtime/memory failure, exceeds the guarded split bounds, changes checkpoint identity, or does not beat the 3% noise floor.

An engine goal kept my current engine

This is deliberate when fewer than two engines are compatible, the matrix is incomplete, greedy output differs, one engine lacks the selected metric, routes began from different thermal states or Low Power Mode settings, starting headroom differed by more than 512 MiB, a speed/latency lead is below 3%, or a memory difference is below 512 MB. Let the Mac settle if needed, then reopen Benchmark Lab and use Compare all engines with the visible contract unchanged.

A previous benchmark result disappeared

Results fail closed when the model or draft file identity, runtime version, hardware fingerprint, client, context/output range, reasoning, sampling, KV mode, or tested accelerator settings no longer match. Re-run the appropriate suite instead of carrying a stale winner across a meaningful change.

Stopping closes something I did not start

It should not. Dedicated oMLX/MTPLX/native-FreeToken processes are tracked by their process group. LM Studio is shared, so Stop unloads only the uniquely named launcher model and leaves the server itself running. Connected FreeToken Stop closes only the launcher's private bridge; it never stops or unloads the remote service.
